### 【ANI-03】（复发，改形）胶囊转场每个已提交帧新建提交回调闭包，「零逐帧分配」承诺仅部分成立

- **位置**：`src/DeskBox/Views/WidgetWindowBase.Collapse.cs:3699–3739`（根因点）；`:4368–4389`（已被缓存保护的下游）。
- **触发条件**：任一胶囊展开/收起转场的每个**已提交**几何帧（每动画窗口每帧一次；被 skip 的 tick 不经过此路径）。
- **风险等级**：P3。
- **潜在影响**：每个提交帧每窗约 3 次小对象分配（1 个编译器闭包显示类 + 2 个委托）。60–165Hz、每窗每秒约 120–330 次；多胶囊并发（1.5.0 起并发上限已放开，见观察项 2）时线性放大。与同管线在 `WidgetCompactAnimationCoordinator.FlushPendingBoundsMoves`（589–592 注释）和 `MoveWindowWithoutPersisting`（4363–4367 注释）明示的零分配纪律不一致。
- **代码层面根因**：DEF-060 修复曾把每帧 4 个闭包归零；DEF-066（e2f09d9）为兼容上游 committed/commitFailed 失败协议重建了回调链——`MoveWindowWithoutPersisting` 内部三个回调用 `??=` 缓存（该半已修好），但**调用方**仍以局部函数形式逐帧传入：

```csharp
// Views/WidgetWindowBase.Collapse.cs:3699–3739（每帧执行）
bool boundsChanged = !BoundsEqual(_collapseAnimationLastCommittedBounds, bounds);
void OnCommitted()
{
    if (generation != _collapseAnimationGeneration) { return; }
    long timestamp = Stopwatch.GetTimestamp();
    double workMs = Stopwatch.GetElapsedTime(frameTimestamp, timestamp).TotalMilliseconds;
    ...
    if (boundsChanged) { _collapseAnimationLastCommittedBounds = bounds; ... }
    completed?.Invoke();
}
void OnCommitFailed() { ... }
if (boundsChanged || completed is not null)
{
    MoveWindowWithoutPersisting(bounds,
        suppressRedraw: completed is null,
        committed: OnCommitted,      // 每帧新委托 + 闭包（捕获逐帧变化的 bounds/frameTimestamp/boundsChanged/completed/generation）
        commitFailed: OnCommitFailed);
}
```

  `OnCommitted` 捕获的 5 个局部/参数逐帧变化，编译器无法缓存；`CollapseAnimationRendering` 的 `progress < 1` 分支（3631–3634）每帧调用一次。
- **整改建议**：把 `bounds/frameTimestamp/generation/boundsChanged/completed` 五项按 DEF-066 同款方式存入字段（帧序一致性由 `_collapseAnimationGeneration` 已有校验保证），`OnCommitted`/`OnCommitFailed` 改为读字段的无捕获实例方法并各缓存一个委托（实例方法组可缓存）。

### 【ANI-07】共享 Composition 动画模板跨次启动反复 InsertKeyFrame，依赖未文档化的重复进度语义，且该 API 无任何清除关键帧的手段

- **位置**：`src/DeskBox/Controls/WidgetShell.xaml.cs:2135–2149`（CompactOpacity：单次收起对 8 个元素各灌 13 帧）、`:2161–2174`（CompactScale：25 帧）、`:2186–2199`（CompactTranslation：25 帧）、`:3067–3078`（CompactLive*，每次 track 宽度变化重启）、`:3273–3278`（EdgeGlow）、`:986–993`（GroupDropBreathing）；`src/DeskBox/Services/WidgetTrayAnimationController.cs:423–424,439–440,542–558`（TrayOpacity/TrayScale，且两端值随显示/隐藏方向不同）；模板容器 `src/DeskBox/Services/WidgetCompositionResources.cs:32–60`。
- **触发条件**：模板复用自 1.5.0 批次（03f0b015）起全面替代逐次 `CreateScalarKeyFrameAnimation`。胶囊悬停展开/收起是全应用最高频动画；每次启动先 `GetScalar/GetVector3` 取回**同一个**长生命周期动画对象，再对其重复 `InsertKeyFrame`。`ResyncCompactTransitionFades`（1933–1947）还会在同一转场内二次重灌。
- **风险等级**：P3（行为依赖未文档化语义；最坏情形为会话级缓慢劣化）。
- **潜在影响**：官方 `KeyFrameAnimation` 公开方法表**没有** `ClearAllKeyFrames`/`RemoveKeyFrame`（Microsoft Learn 类页面核实，2026-09），即关键帧一旦插入在 API 层面无法移除。若运行时对重复 normalizedProgress 是**追加**：模板对象上的关键帧随使用单调增长（收起一次 ≈ 8×13+2×25 ≈ 154 帧/窗；重度悬停用户每天数千次 → 数十万关键帧/模板），`InsertKeyFrame` 与 `StartAnimation` 快照成本随长度线性上升，表现为「用得越久、胶囊转场启动越慢」+ 原生内存缓涨；若运行时是**替换**则无影响。本专项无法静态判定二者（无公开文档），但两分支中较优分支也意味着整条热路径的正确性建立在未文档化行为上。
- **代码层面根因**：模板复用只考虑了「StartAnimation 取快照，改模板不影响已运行的动画」（`WidgetCompositionResources.cs:20–24` 注释），未考虑关键帧集合的累积。注意 `WidgetTrayAnimationController` 的 TrayOpacity 模板两端值随方向变化（423–424 vs 542–543），若为追加语义，交付曲线还会依赖引擎对同进度多关键帧的取舍——当前生产中 tray 动画表现正常，构成「非最坏语义」的间接旁证，但不能排除内部列表仍在增长。
- **代码证据**：

```csharp
// WidgetShell.xaml.cs:2135–2151（每次转场、每个元素执行，模板对象常驻）
ScalarKeyFrameAnimation animation = _compositionResources.GetScalar(
    visual.Compositor, WidgetAnimationTemplate.CompactOpacity);
...
animation.InsertKeyFrame((float)timeProgress, ...);   // ×13，无任何清除步骤
visual.StartAnimation("Opacity", animation);

// WidgetCompositionResources.cs:37–40（同一实例反复返回）
if (_animations.TryGetValue(template, out CompositionAnimation? existing))
{
    return (ScalarKeyFrameAnimation)existing;
}
```

- **整改建议**：①在运行时以 `animation.KeyFrameCount` 一次性验证语义（若重复启动后计数不增长则本条降级为注释加固）；②无论语义如何，模板重灌前固定调用清除（若确认引擎无清除 API，则对「值随调用变化」的模板——TrayOpacity/CompactLive*/GroupDropBreathing——退回逐次新建动画对象，仅保留「值恒定」的模板复用），或改用 ExpressionAnimation 参数化替代重灌。

## 4. 观察项

1. **群组标题切换对 `FrameworkElement.Width` 做依赖（逐帧布局）动画**：`Controls/WidgetGroupTitleSwitcher.Interaction.cs:836`（`EnableDependentAnimation = true` + `SetTargetProperty(widthAnimation, nameof(FrameworkElement.Width))`）。Width 无法走合成器线程，该标志是功能必需；但每次标题 tab 切换的整个 duration 内 UI 线程逐帧 measure/arrange。低频、时长有界，暂不立案；若卡片数量/嵌套加深可考虑改 Clip/Translate 方案。
2. **胶囊转场并发上限名存实亡**：`Services/WidgetCompactAnimationCoordinator.cs:25` `MaximumConcurrentBoundsTransitions = int.MaxValue`（round-06 记录为 4，含 `InvalidOperationException` 防御）。`HasBoundsTransitionCapacity` 恒真，`WidgetWindowBase.Collapse.cs:3399` 的容量检查与 `WidgetCompactAnimationConcurrencyPolicy` 成为空转；`PendingBoundsMoves` 批量提交本身可承载任意并发，无功能性风险，但防御性上限（防极端场景 DWM 批量过载）与 round-06 记录、测试语境脱节，属 1.5.0 批次有意/无意放开，建议恢复一个有限上限或在注释中记录取舍。
3. **Glance 图片过渡中止后旧位图滞留一个周期**：`Controls/WidgetContents/GlanceWidgetContent.xaml.cs:947–1001`——`_transitionStoryboard?.Stop()` 后 `Completed`（993–999）不触发，`outgoing.Background`（旧 BitmapImage）与 `_isAActive` 留存至下一次成功过渡才被清理/校正。最多滞留一张解码位图，自愈，仅在快速连续切换图片时短暂多占内存。
4. **`ResolveSkipForFrameRate` 非整除超调**：100/110Hz 等非整倍刷新率下，60/90/120 档会交付高于档位的节奏（如 100Hz+60 → 100fps），符合「不低于所选」契约但与档位语义（用户要求降帧省电）有偏差；当前主流刷新率（60/90/120/144/165）受影响面小，留意即可（与 ANI-08 的注释修正一并处置即可）。
5. **帧率档位不影响 tray 动画**：cap 仅接入 `BeginWidgetCollapse`（胶囊转场）；tray 批量/单窗动画（`WidgetTrayAnimationController`/`WidgetTrayBatchAnimationDriver`）仍按显示刷新率全速（round-06 §4-3 结论不变）。符合 VERIFY-1 范围（悬停展开），非缺陷，记录为语义边界。
6. **DEF-083 维持原状**：`ContentWidgetWindow.xaml.cs:858–870` `_autoRestoreTimer` 到点仍无条件 `RestoreDesktopLayer(force:true)`，未加「托盘唤起会话」护栏——台账挂账未变化，非本轮新发现。
