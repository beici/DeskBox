## 3. 问题清单

### EXC-08【恢复归档含重复 manifest.json 条目时异常逃出用户面映射，显示英文运行时消息】
- **位置**：`src/DeskBox/Services/DeskBoxDataBackupService.cs:1684`（SingleOrDefault）、`:1724-1726`（映射过滤器）；`src/DeskBox/Views/SettingsWindow.CloudBackup.cs:452-469`（FormatBackupError 回退 `ex.Message`）
- **触发条件**：用户选择一个被篡改/异常工具写出的 zip，其中 `manifest.json` 条目出现两次。
- **风险等级**：P3
- **潜在影响**：`archive.Entries.SingleOrDefault(...)` 抛 `InvalidOperationException`（"Sequence contains more than one matching element"）。`ExtractAndValidateManifestAsync` 的重映射过滤器只匹配 `InvalidDataException or JsonException or NotSupportedException`，该异常不被翻译为带 `BackupManifestInvalidDataKey` 的 InvalidDataException，一路传播到恢复对话框，`FormatBackupError` 回退显示原始英文运行时消息，而非「备份清单不可读」的本地化文案。不崩溃、不损坏数据（Prepare 阶段 catch 后清理 staging 并重抛）。
- **代码层面根因**：manifest 唯一性假设内嵌在 `SingleOrDefault`，其异常类型未被纳入同一InvalidDataException 归一化通道。
- **代码证据**：
  ```csharp
  // DeskBoxDataBackupService.cs:1684
  ZipArchiveEntry? manifestEntry = archive.Entries.SingleOrDefault(entry =>
      string.Equals(entry.FullName, "manifest.json", StringComparison.Ordinal));
  // :1724-1726 —— 过滤器不含 InvalidOperationException
  catch (Exception ex) when (
      (ex is InvalidDataException or JsonException or NotSupportedException) &&
      !ex.Data.Contains(BackupManifestInvalidDataKey))
  // SettingsWindow.CloudBackup.cs:469 —— 未识别类型回退 ex.Message
  return ex.Message;
  ```

### EXC-09【WebDAV PROPFIND 响应中畸形 href 抛 UriFormatException，未被归入传输异常分类】
- **位置**：`src/DeskBox/Services/WebDavBackupTransport.cs:243-246`（`new Uri(href)`）、`:228-231`（仅捕获 XmlException）
- **触发条件**：服务器（或中间代理）返回的 multistatus 中某 `<href>` 以 "http" 开头但不是合法绝对 URI（如 `http://[::bad`、含空格的畸形串）。
- **风险等级**：P3
- **潜在影响**：`ParseMultistatus` 只把 XmlException 翻译为 `CloudBackupTransportException`；`UriFormatException`（服务端可控输入触发）裸抛，导致 ListAsync/上传列表验证（VerifyUploadAsync）/保留清理（ApplyRetentionAsync）/恢复快照列表全部中断：计划路径记一次去重日志并打失败戳（不崩溃），手动路径在设置页显示未分类的运行时消息。仅显示与重试语义受损，无数据损失。
- **代码层面根因**：对 href 的「http 前缀 ⇒ 绝对 URI」判断缺少 TryCreate 式容错；异常归一化只覆盖 XML 解析层。
- **代码证据**：
  ```csharp
  // WebDavBackupTransport.cs:243-246
  string decodedPath = Uri.UnescapeDataString(
      href.StartsWith("http", StringComparison.OrdinalIgnoreCase)
          ? new Uri(href).AbsolutePath     // 畸形 href → UriFormatException 裸抛
          : href);
  // :228-231 —— 仅 XmlException 被翻译
  catch (System.Xml.XmlException ex)
  { throw new CloudBackupTransportException("The server returned an invalid PROPFIND response.", inner: ex); }
  ```

### EXC-10【合并模式恢复对 id=null 的暂存条目抛 ArgumentNullException，该域恢复确定性失败直至放弃】
- **位置**：`src/DeskBox/Services/DeskBoxDataBackupService.cs:1519-1543`（`MergeStagedTodoStoresAsync`）、`:1589-1622`（`MergeStagedQuickCaptureStoreAsync.MergeList`）
- **触发条件**：云备份 zip 内某 todo.json / quick-capture.json 携带 `"id": null`（手编、第三方工具产出或损坏）。`ValidateScopedRestoreData`（:713-751）只验证「能反序列化且非 null 文档」，不校验条目 id。
- **风险等级**：P3
- **潜在影响**：合并索引是 `Dictionary<string,int>`，`liveIndexById.TryGetValue(item.Id, …)` / `liveIndexById[item.Id] = …` 遇 null key 抛 `ArgumentNullException`；异常被 `ApplyScopedRestoreCoreAsync`（:1420-1457）捕获后按 `ApplyAttemptCount` 重试，3 次后放弃该恢复并留日志。结果 graceful（marker/staging 清理、pre-restore 安全 zip 兜底、非 null 条目不受影响），但该域恢复永远无法完成且用户得到的失败消息不含「哪条数据坏了」。
- **代码层面根因**：Id 在模型上有默认值（`TodoItem.cs:26` / `QuickCaptureItem.cs:5` 均 `= Guid.NewGuid().ToString("N")`）但 JSON 显式 null 可覆盖；合并索引未对 null id 做跳过防御。
- **代码证据**：

  if (!liveIndexById.TryGetValue(item.Id, out int index))   // item.Id == null → ArgumentNullException

## 4. 观察项（证据成立但不足立案或属设计取舍）

1. **覆盖模式恢复先删后拷的中间态**：`ApplyScopedRestoreCoreAsync`（DeskBoxDataBackupService.cs:1350-1361）先删除域内存活文件再拷贝暂存文件；拷贝中途失败进入重试预算，重试耗尽放弃后（:1426-1437）该域文件留空，恢复依赖 `EnsurePreRestoreSafetyBackupAsync` 的 pre-restore zip 手工恢复。代码注释已明示该取舍（重试有界防死循环），属已记录的设计决策，仅建议放弃路径的通知文案提示用户安全 zip 的位置。
2. **活体文件 DOM 解析无 try**：`WidgetStyleBackupProjection.ApplyAsync`（:217、:266）对 live settings.json / widget-layout.json 的 `JsonNode.Parse` 未捕获 JsonException；依赖上层 retry/abandon 通道，失败语义一致但错误归因不含「活文件损坏 vs 归档损坏」区分。
3. **Sync 预留层零生产调用**：`SyncProjection/SyncOutboxStore/SyncRevisionsStore/SyncStateStore/SyncEnvelope` 当前无任何生产调用方（仅测试引用）。`SyncProjection.cs:121-124/258-261` 的 `File.Exists → BlobRefAsync(FileStream)` 存在 TOCTOU（文件在两步间消失则 IOException 裸抛）；接线前应补。现在不构成生产缺陷。
4. **DirectStartupService.GetStateCore 静默 catch**（:106-109）：任何注册表/任务查询异常归一为 `BlockedOrFailed` 且无日志，自动化状态排障缺线索（同类 `IsRunEntryApproved` :420-423、`IsLegacyShortcutOwnedBy` :498-501）。
5. **导航回滚路径吞 watcher 重建失败**：`WidgetViewModel.Navigation.cs:291-298/309-316` 回滚 `ConfigureFolderWatchersAsync(previousPath)` 的 catch{} 丢失失败细节——导航本身已失败，仅诊断面受损。
6. **Log 路径空 catch 注释缺失**：`App.xaml.cs:726/794`（Log 入队 / DrainLogQueue 落盘）round-06 时代注释已不在，行为正确（日志系统不可自爆）。
7. **正面确认（新增面）**：`StartupPipeline`（WriteSummary 双层 try 防自爆）、`WidgetLayoutStore`（fail-closed 结构校验 + CanWrite 只读立场 + RevertLastCommit）、`SettingsService.SaveToFileOnlyAsync`（双文件提交失败回滚 layout commit，:942-1010）、`SyncRevisions/SyncStateStore`（fail-closed 结构校验 + 写时 schema 门）、`DirectStartupTaskXmlReader`（COM 生命周期 finally 全量释放 + RPC_E_CHANGED_MODE 语义）、`CloudBackupService`（gate 序列化、superseded-options 失败戳隔离、retention 夹紧、verify 降级不误报）、`MemoryReclaimer`/`HookHealthWatchdog`（全路径 try + 状态化结果）、`ParseMultistatus` 禁 DTD、manifest 解压 zip 炸弹预算 + 路径逃逸/重复条目校验、`ExtractAndValidateManifestAsync` 的 `checked` 总量累加：新代码异常纪律整体显著高于旧代码均值。
