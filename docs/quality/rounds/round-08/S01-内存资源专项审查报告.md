### 【MEM-03】`NativeFileDragOut.BeginFileDragOut` 的拖拽饥饿看门狗 Timer 在方法返回瞬间即被 Dispose，永不触发

- 【位置】`src/DeskBox/Helpers/NativeFileDragOut.cs:255-271`（`using var watchdog = new System.Threading.Timer(...)`）；`:273-311`（拖拽工作项入队后方法即返回）
- 【触发条件】任意一次原生拖出（widget 文件拖出到 Explorer，1.5.x 新链路）。`BeginFileDragOut` 是同步方法：创建 15s 周期看门狗 → `queue.TryAdd(work)` → **方法返回**，`using var` 语义在返回点立即 `Dispose` 该 Timer。
- 【风险等级】P3
- 【潜在影响】无内存泄漏（恰恰是被过早释放）；后果是设计目标失效——注释声明的「QueryContinueDrag 从未被调用 = 拖拽循环饥饿并持有系统级 OLE 拖拽锁」的 15s 周期诊断日志（`:256-267`）永远不会出现，字段排障时缺失该关键信号。该 Timer 的全部生命周期（创建即销毁）均在同一线程内，无跨线程竞态。
- 【代码层面根因】把「随拖拽会话存活的看门狗」误写成「随方法作用域存活的局部资源」。`using var` 的释放点是 `BeginFileDragOut` 的作用域末尾，而非 `work` 闭包执行完毕时；正确的配对点应是 `work` 内 `finally`（与 `Interlocked.Exchange(ref done, 1)` 同处）或改为在完成回调中 `Dispose`。
- 【代码证据摘录】
  ```csharp
  // NativeFileDragOut.cs:255-273（BeginFileDragOut 内，同步方法）
  using var watchdog = new System.Threading.Timer(
      _ => {
          if (Volatile.Read(ref done) == 0 &&
              ReferenceEquals(Volatile.Read(ref s_activeDropSource), source) &&
              source.QueryContinueCount == 0)
          { App.Log("[NativeDragOut] WATCHDOG: QueryContinueDrag was never called ..."); }
      },
      null, TimeSpan.FromSeconds(15), TimeSpan.FromSeconds(15));
  _ = queue.TryAdd(() => { ... });   // 入队后方法返回 → using var 在此 Dispose watchdog
  ```
