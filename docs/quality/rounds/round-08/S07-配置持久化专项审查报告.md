## 3. 问题清单（round-08 编号，CFG-01 起）

### 【CFG-01】settings.json 是全仓唯一没有「更新版本架构」写保护的 owned store：老构建读新档案后首次保存即静默丢弃未知字段

- 【位置】`src/DeskBox/Services/SettingsService.cs:705-868`（`LoadAsync`，对 `SchemaVersion > CurrentSchemaVersion` 无任何拒绝/只读分支）、`:942-1058`（`SaveToFileOnlyAsync` 无写前门禁）；对照同仓库已实现该防护的三处：`WidgetLayoutStore.cs:98`（`CanWrite => _loadedSchemaVersion <= CurrentSchemaVersion`，refuse-to-overwrite 注释明言「the typed slice cannot represent its unknown fields」）、`SyncRevisionsStore.cs:105-115`（写入前重读磁盘版本戳，新于己即抛 `InvalidDataException`）、`WeatherCacheStore.cs:192-196`（版本超出即弃用缓存）
- 【触发条件】①降级/回滚：用户从新版回退到旧版（本仓库发布节奏快、以直发更新为主，回滚现实存在）；②fork ↔ upstream 交叉使用：upstream v1.5.5 二进制打开本 fork 的档案（fork-only 字段如 `widgetTitleAlignment`、`widgetAnimationFrameRate` 不在 upstream 类型图中）。`System.Text.Json` 类型化反序列化静默丢弃目标类型不认识的成员（`AppSettings` 无 `JsonExtensionData`，全仓 grep 证实），且 `RunMigrationsOnCopy` 对 `SchemaVersion >= CurrentSchemaVersion` 早退不降版（`SettingsMigrationService.cs:69-72`），于是归一化照常执行、首次 `SaveDebounced`/`SaveAsync` 即把删掉未知字段后的图写回磁盘——版本号保持新值、字段已丢失，完全静默。
- 【风险等级】**P2**（低频场景但后果为不可逆静默配置丢失；且防护模式在本仓其余三个 owned store 已是既定约定，settings.json 作为最大、最重要的 store 反而缺席，属防护不对称）
- 【潜在影响】降级会话内改任何一项设置即触发全量重写：新版引入的全部字段（含 fork-only 的标题对齐、帧率上限，若切到 upstream 构建）连同值一起消失；用户无任何感知，重装新版后无法恢复（.bak 也已被新写覆盖）。
- 【代码层面根因】settings.json 的版本契约只有「向后迁移」（低版本→当前），没有「向前只读」（高版本→本构建拒写）；`SaveToFileOnlyAsync` 只门禁 widget-layout 的新架构（:960-975），对 settings 自身 SchemaVersion 不做任何检查。
- 【代码证据】
  ```csharp
  // SettingsMigrationService.cs:69-72 —— 新版本早退，不降级也不拒绝
  if (settings.SchemaVersion >= CurrentSchemaVersion)
  {
      return (settings, false);
  }
  // WidgetLayoutStore.cs:96-98 —— 同仓库既定防护（settings.json 无对应物）
  // writing it back would silently discard the newer fields —
  // the store refuses to overwrite and the pristine file remains
  // the authority for a future build that can read it.
  internal bool CanWrite => _loadedSchemaVersion <= CurrentSchemaVersion;
  // SettingsService.cs:960-964 —— 保存门禁只覆盖 layout，不覆盖 settings 自身
  if (Layout.IsAuthoritative)
  {
      if (Layout.CanWrite) { layoutSaved = await Layout.SaveCheckedAsync(...); }
  ```
- 【整改建议】仿 `WidgetLayoutStore.CanWrite`：LoadAsync 检出 `SchemaVersion > CurrentSchemaVersion` 时置「只读会话」标志（可复用 `LastLoadRecoveryState` 通道或新增状态），`SaveToFileOnlyAsync` 在该状态下拒写并走 `PersistenceFailed` 上报；或最低成本方案——写前重读磁盘版本戳（同 `SyncRevisionsStore` 模式）。降级场景另需考虑类型图外字段的最小保留（`JsonExtensionData` 兜底袋）。

### 【CFG-02】LoadAsync 外层 catch 恢复档案仍以 SchemaVersion=1 落盘（DEF-075 残余面：内层恢复路径已修、外层兜底未修）

## 4. 观察项（证据不足立案或影响极低，仅记录）

- **O-1** `WriteSettingsTempFileAsync`（`SettingsService.cs:1084-1095`）的写前归一化集比 `LoadAsync`（:788-801）少 `DataBackupSettingsPolicy.Normalize`。当前无功能影响（手改文件只在启动时读取、写路径归一化是冗余防御），但两份归一化清单是手工维护的平行清单，新增归一化时易漏。
- **O-2** `WidgetStyleBackupProjection.RestoreJournalSnapshotAsync`（`WidgetStyleBackupProjection.cs:426-435`）恢复日志快照用裸 `File.WriteAllTextAsync` 写主文件与 .bak，非原子；因日志文件在清理前保留、下次 apply 幂等重跑，崩溃可自愈，不立案。
- **O-3** `SettingsService.LoadAsync:810-811` 把活 slice（`_settings.WidgetLayout`）直接作为 seed 传给 `Layout.LoadAsync`，其 `DefaultMissing` 分支序列化 seed 时未持 `_lock`（`WidgetLayoutStore.cs:191, 262-271`）；仅发生在启动期 UI 未起之前，无现实竞争。
- **O-4** Sync 引擎当前只有投影（`SyncProjection`）+ outbox/revisions/state 三个 store，push/pull/还原端未接线；`SyncOutboxStore.DequeueAsync`（`SyncOutboxStore.cs:126-136`）`File.Delete` 在文件被占用时会抛 IOException（合同注释以「重推幂等」兜底）。还原端落地时需按 §2.3 复核 blob→payload 映射与墓碑消费。
- **O-5** DEF-067 修复后的快照测试仍存在理论窗口：`WaitForStagedFileAsync` 等待的是暂存文件「存在」而非「复制完成」（`DeskBoxDataBackupServiceTests.cs:1170-1182` vs `CopyStableSnapshotFileAsync` 的 CreateNew→复制完微秒间隙），且测试载荷 Light/Dark 等长（21 字节）可同时通过长度+时间戳校验；实际触发概率远低于原闪断，维持观察。
- **O-6** `SettingsMigrationService.cs:216-267` `Migration_1_To_2` 与 `Migration_2_To_3` 的重复段维持（台账既有条目，P3 卫生项，未触及）。
- **O-7** widget-layout.json 一旦权威（authoritative），settings.json 不再携带 11 个布局键（`SettingsService.cs:1096-1120` strip 投影 + `WidgetLayoutStore.SettingsWireKeys`）——老构建降级将读不到布局（widget-layout.json 对其不可见）。设计文档已明示该前向取舍（fail-closed 采纳协议 + 崩溃窗口零丢失），不立案；但与 CFG-01 叠加后，「降级 + 布局键已剥离」的档案损失面更大，修复 CFG-01 时应一并评估。

## 5. 小结

配置持久化主链路在 round-08 处于历史最佳状态：ResilientJsonStore 新增双 store 提交回滚与流式写入；迁移管道重写为 copy-on-write 检查点语义（CFG-05/DEF-074 闭环）；Todo/QuickCapture 墓碑与 scoped restore 的合并/替换两套语义、域路径单源（CloudBackupDomains）、归档抽取的实际字节封顶、pending marker 有界重试、widget-style 两文件日志事务，均属高质量实现；round-06 的 9 项发现 7 项闭环、2 项维持（均为挂账 P3，位置与机制完全未变，无复发）。

本轮新立案 **2 项：P0×0、P1×0、P2×1、P3×1**。唯一 P2（CFG-01）指向一个结构性防护缺口：仓库已为 widget-layout.json / sync revisions.json / weather-cache.json 建立了「新架构档案只读」约定，唯独承载最多字段的 settings.json 缺席——在降级回滚与 fork/upstream 交叉使用都是现实工作流的前提下，这是上游合入面当前最值得补的一块板。P3（CFG-02）为 DEF-075 的残余面，一行对齐修复。
