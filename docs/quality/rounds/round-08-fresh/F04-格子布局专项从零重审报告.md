## 2. 问题清单

### FLAY-01 胶囊栏过载时先压碎胶囊尺寸、后挤间距，与注释声明的优先级相反，且最小尺寸下限不随 DPI 缩放

- 位置：`E:\DeskBox\src\DeskBox\Services\WidgetCapsuleArrangementCalculator.cs:145-148`（间距钳制）、`:159-166`（尺寸压碎）、`:197-227`（LAY-04 间距挤压/截断，位于压碎之后）；`:12-13`（DPI 无关的物理常量下限）。
- 触发条件：胶囊栏（Bar 排列模式）单屏成员的"尺寸和 + 间距×(n−1)"超过工作区长度，且把间距先钳到 `safeAvailable/(count−1)` 后 `availableForItems` 小于成员自然尺寸和。实测量级：1080p@100% 竖排（工作区≈1040px、胶囊高 42px）约 15 个胶囊且间距取上限 32 逻辑 px 即进入压碎带；约 20 个胶囊时被压到 ~21px（自然值一半），而 32px 间距原样保留（挤压后 432+32×19=1040 恰好不大于上限，不触发归零）；若默认间距 8px 则需 21+ 个胶囊才轻微压缩。横排同理（Summary 宽 248px 时约 8 个胶囊开始收缩 ~15%）。
- 风险等级：P2。
- 潜在影响：整条胶囊栏的胶囊被等比压扁（极端计数下趋近 1px 细条），`ApplyCompactArrangement(bounds, constrainSize: true)` 按被压尺寸改写窗口并作为会话内槽位（`_lastCapsuleBarBounds`）参与后续拖动/重排，视觉上内容被裁剪；降低间距或减少胶囊数后自愈，无数据损坏。
- 代码层面根因：`FitPrimarySizes` 的三步顺序——先把间距钳到 `safeAvailable/(count−1)`、再用 `availableForItems` 缩放尺寸——使得"间距优先占满、尺寸被压碎"成为中等过载带的行为；而 LAY-04 注释明确声明正确优先级是"Squeeze spacing to zero first (the sizes still win)"，但该挤压在代码中位于尺寸压碎之后，只有当压碎后的总和仍放不下时才执行，永远无法回滚已发生的压碎。另外 `effectiveMinimum = Math.Min(preferredMinimum, Math.Max(1, availableForItems / count))` 让 96/36 的"下限"在整数除法下退化为 1，且 `HorizontalMinimumWidth=96`/`VerticalMinimumHeight=36` 是物理像素常量（`:12-13`），在 200% DPI 下等效逻辑下限减半（18 逻辑 px），与整条链路"逻辑存储、物理计算"的换算惯例不一致。
- 代码证据（摘录）：
  ```csharp
  // :145-148  间距先钳到均分上限，可吃掉几乎全部可用长度
  if (count > 1) { safeSpacing = Math.Min(safeSpacing, safeAvailable / (count - 1)); }
  int availableForItems = Math.Max(1, safeAvailable - safeSpacing * Math.Max(0, count - 1)); // :153
  // :159-166  尺寸按剩余空间压碎，下限可退化为 1
  int effectiveMinimum = Math.Min(preferredMinimum, Math.Max(1, availableForItems / count));
  double scale = availableForItems / (double)Math.Max(1, sizes.Sum());
  sizes[index] = Math.Max(effectiveMinimum, (int)Math.Floor(sizes[index] * scale));
  // :205-210  间距归零发生在压碎之后，无法挽回已压碎的尺寸
  int totalWithSpacing = sizes.Sum() + safeSpacing * Math.Max(0, count - 1);
  if (totalWithSpacing > safeAvailable && count > 1) { safeSpacing = 0; totalWithSpacing = sizes.Sum(); }
  ```
  对照注释 `:197-204`："Squeeze spacing to zero first (the sizes still win), then truncate the tail" —— 与实际执行顺序不符。测试 `WidgetCapsuleArrangementCalculatorTests.cs:120-156` 只覆盖了"count×1px+spacing 仍放不下"的极端截断分支，未覆盖"归零间距即可全尺寸放下"的中等过载带。

### FLAY-02 普通拖动的吸附目标与工作区在拖动开始时一次性快照，跨屏拖动在新显示器上既不吸附屏幕边缘，间距/阈值也沿用源屏 DPI

- 位置：`E:\DeskBox\src\DeskBox\Services\ResizeGuideOverlayService.cs:688-702`（`BeginDrag` 一次性快照）、`:710-748`（`UpdateGuidesAndSnapForDrag` 每帧复用快照，无重解析）、`:299-309`（`ConfigureSessionSnapMetrics` 用拖动起始窗口的 DPI 换算间距/阈值）；对照实现：`E:\DeskBox\src\DeskBox\Services\WidgetManager.CapsuleArrangement.cs:861-871`（`UpdateDragWorkArea` 胶囊栏拖动逐帧重解析工作区）。
- 触发条件：拖动任一未收起 widget 从显示器 A 跨到显示器 B（非 Ctrl 协同移动、非胶囊栏拖动）。
- 风险等级：P3。
- 潜在影响：在显示器 B 上拖动时，工作区吸附候选仍是 A 屏工作区（永远差一屏距离，不触发），B 屏边缘无对齐吸附；`GetOtherWidgetBounds` 快照也只含拖动开始时刻的窗口（拖动期间静止，此项影响小）；跨 DPI 时 engage/release 阈值与间距按 A 屏比例换算成物理值，在 B 屏上手感偏大/偏小。功能不失效，属跨屏体验降级，且与胶囊栏拖动"逐帧重解析"的行为不一致。

### FLAY-03 初始摆放补偿（PlacePendingInitialWidgets）的级联偏移在 EnsureVisible 之后做减法，无再钳制，可把宽 widget 推出工作区左缘

## 3. 观察项

（证据已核实，但触发概率极低、属设计取舍或影响不足以立案）

1. **胶囊排列结果的字典直索引缺防御**：`WidgetManager.CapsuleArrangement.cs:646` `RectInt32 target = arranged[member.Config.Id];` 假设 `WidgetCapsuleArrangementCalculator.Calculate` 为每个成员返回条目；仅当 `FitPrimarySizes` 截断尾部（需成员数 > 工作区像素长度，约需上千个胶囊）或 `workArea ≤ 0` 时才可能缺键并抛 `KeyNotFoundException`。当前实际不可达，但 `TryReorderCapsuleBarMember`（同文件 `:333-343`）用 foreach 遍历结果的写法更稳，建议统一为 TryGetValue。同路径 `Calculate` 的空结果分支（`workArea.Width<=0`）同样依赖 `GetFromRect` 永不返回零尺寸工作区的假设。
2. **EnsureVisible 对超宽 widget 的"固定点"漂移为已记录的已知局限**：`WidgetPositioningService.cs:268-283` 的 fallback 分支注释自述"更宽的 widget 重启后锚点翻转、落点会轻微漂移后稳定"；当前唯一无钳制的定位入口（边距对话框 `ShiftSideToMargin`）已在 `WidgetWindowBase.TitleAppearance.cs:1049-1052` 补了 `EnsureVisible`，仅剩此自洽性问题，无行动需求。
3. **跨 DPI 拖动不重缩放窗口物理尺寸，逻辑尺寸随落屏重新归一**：拖动中 `WM_DPICHANGED` 恢复被刻意抑制（`WidgetDisplayChangeWatcher.cs:39-57` 注释声明用户最终落点权威），落屏后 `UpdateConfigFromPhysicalBounds`（`ContentWidgetWindow.xaml.cs:559-592`）按新屏 DPI 把物理尺寸换算为新逻辑值——widget 在高 DPI 屏上内容密度变小、与其它屏观感不一致；往返拖回后逻辑尺寸复原，重启后解析自洽，无漂移。属设计取舍，建议知悉（Windows 惯例是按 WM_DPICHANGED 建议矩形重缩放）。
4. **批量边距"应用到全部"使用移动前单一快照**：`WidgetManager.BulkAppearance.cs:97-118` 先快照全部可见窗口矩形，`:146-154` 每个 transform 收到的"邻居"均来自该快照；窗口逐个 `SetWindowPos`（`:156`）后快照不更新，后处理的 widget 参考的是邻居的旧位置，批量结果与逐个单独设置会不一致，极端时可相互重叠。单 widget 路径无此问题。
5. **跨屏放置的骑跨矩形会在下次解析时收进单屏**：`CapturePositionAnchor` 用窗口中心选屏（`WidgetWindowBase.Bounds.cs:526-544`），`CaptureAnchorCore` 对越出中心屏的边距 `Math.Max(0, …)` 归零（`WidgetPositioningService.cs:224-225`）；故意把 widget 骑跨两屏落下后，重启/拓扑解析会把整窗拉回中心屏工作区内。锚点模型的固有行为，仅提示。
6. **新建功能 widget 全部落在 (100,100) 物理像素且无级联**：`WidgetConfig.cs:23-26` 默认 X=Y=100，Todo/音乐/天气/搜索/速览等创建路径（`WidgetManager.FeatureWidgets.cs:88-95`、`:147-154`、`WidgetManager.cs:1119-1128`）均未设置初始位置或级联偏移，只有首个文件 widget 走 `InitialFileWidgetPlacementPolicy`（指针位置/右上对齐）。连续创建多种功能 widget 会完全重叠堆放于主屏同一点，用户可能察觉不到新 widget 已创建。建议与 `PlacePendingInitialWidgets` 的级联逻辑统一。
7. **胶囊栏重排序拖动中途即持久化顺序**：`TryReorderCapsuleBarMember`（`WidgetManager.CapsuleArrangement.cs:310-316`）在拖动帧内就把合并后的顺序写入 `settings.WidgetCapsuleBarOrder`；Esc/捕获丢失仍会走 `CompleteCapsuleBarDrag` 落盘，因此不存在"取消重排"语义。行为可接受，仅记录与其它拖动（落点才提交）的不一致。
8. **已核对无问题的重点**（避免复核浪费）：`TransferCapsuleIdentity` 的"删目标、替换源槽"位次数学在多目标/交叉次序下均正确（`WidgetManager.Groups.cs:2563-2593`）；`WidgetCapsuleOrderCalculator.MoveToNearestSlot` 的先删后插语义符合"移动到目标槽"预期；`WidgetGroupOrder.MoveAndSaveAsync` 持久化失败回滚、`WidgetGroupMutationSnapshot` 对布局/胶囊身份的快照恢复完整；`WidgetLayoutStore` 的 fail-closed 采纳、schema 新于构建时拒写、settings.json 键条带化设计闭环；拓扑 `MapToTopology` 对尺寸/边距按有效面积比缩放并全程钳制（`WidgetTopologyLayoutService.cs:410-521`）；`WidgetGroupConfig`/`WidgetCompactPlacement` 的 `BoundsCoordinateVersion` 默认值无旧数据缺字段风险（git 确认字段与组功能同期引入）。
