## 2. 问题清单

### FWIN-01 Show Desktop 自愈的 DWM cloak 检测只识别 CLOAKED_APP(1)，shell cloak(2) 与继承 cloak(4) 全部漏检（P2）

- 位置：`src/DeskBox/Services/WidgetManager.ShowDesktop.cs:82-90`；`src/DeskBox/Platform/Win32Helper.cs:1919-1937, 1984`
- 触发条件：静置格子因 desktop-owner 挂接失败而落入普通顶层带（该服务的存在前提），之后被 Shell 侧 cloak（Show-Desktop cloak 类路径/继承 cloak），且 `IsTrayCloakActive` 为 false。
- 风险等级：P2（低频/边界场景，但直接命中该自愈服务的功能目的；注释与 DWM 常量语义失同步客观成立）。
- 潜在影响：此类格子持续不可见，直到一次无关的前台/Z-order 事务碰巧触发恢复——即该服务文档自述要消除的"Show Desktop 后部分格子不回来"症状在 cloak 值≠1 时复现。
- 代码层面根因：`DWMWA_CLOAK` 是标志集（dwmapi.h：`DWM_CLOAKED_APP=1`、`DWM_CLOAKED_SHELL=2`、`DWM_CLOAKED_INHERITED=4`），代码与辅助函数注释均按布尔（0/1）处理，判等 `== 1` 只覆盖"被其属主应用 cloak"。本仓唯一 cloak 写入方是托盘动画控制器（`WidgetTrayAnimationController.cs:124-152`，且已在 `ShowDesktop.cs:62-67` 被 `IsTrayCloakActive` 排除），因此 `==1` 在生产中几乎不可能命中本服务针对的场景。
- 代码证据（`WidgetManager.ShowDesktop.cs:82-90`）：
  ```csharp
  if (Win32Helper.TryGetDwmCloakState(hwnd) == 1)
  {
      int visible = 0;
      Win32Helper.TrySetDwmWindowAttribute(hwnd, Win32Helper.DWMWA_CLOAK, ref visible);
      uncloaked++;
      App.Log($"[ShowDesktop] Uncloaked shell-cloaked resting widget ...");
  }
  ```
  （`Win32Helper.cs:1921-1922` 注释：`"...the raw DWMWA_CLOAK value (0 visible, 1 cloaked)"` —— 与掩码语义不符。）说明：Shell 实际使用的 cloak 值无法静态确证（可能随系统版本不同），但 `!= 0`（在排除自身托盘 cloak 前提下）才是与本服务文档目的一致的判据；现值无论取何 cloak 路径都过窄，且 `==1` 与"shell-cloaked"日志文案互相矛盾。

## 3. 观察项

1. `ContentWidgetWindow.EnsureRaisedFromTrayTopMost`（`ContentWidgetWindow.xaml.cs:952-963`）对已可见格子使用 `AppWindow.Show()` + `ShowWindow(SW_SHOWNORMAL)`（激活语义），与 `ShowWithoutActivation` 的 `SW_SHOWNOACTIVATE` 路径不一致。重复托盘唤起时每个可见格子都经历一次激活性 Show + `BringToFront` + `HoldTemporaryTopMost`；手册将多次带迁移定性为有意保留，但 SW_SHOWNORMAL 的中间激活副作用未见专门决策记录。
2. `RaiseWidgetsFromTrayCoreAsync`（`WidgetManager.TrayAnimation.cs:109`）直接字段写 `_widgetsRaisedFromTray = windowsToRaise.Count > 0` 绕过 `SetWidgetsRaisedFromTray` 的会话状态机与事件，随后在 `:138` 再经状态机收敛。两写点之间无 await、同线程同步，现状安全，但属隐性双写契约。
3. `TryRestoreRaisedWidgetsAfterInteraction`（`WidgetManager.ZOrder.cs:911-918`）把 `GetForegroundWindow()==0` 读作"仍属我们"并跳过本 tick；依赖监视器下个 tick 重试。持续 Zero 前台的异常会话会无限保活唤起态（有 toggling/交互/抑制窗三道闸兜底，风险低）。
4. `App.IsDeskBoxWindow`（`App.xaml.cs:674-709`）按进程 PID + 已知根窗口判定，范围宽（本进程所有窗口前台都会保持唤起态）；技术手册已自述此特性，仅备忘。
5. `PrepareTrayShowAnimationCore` 返回 `prepared && boundsRetargeted`（`ContentWidgetWindow.xaml.cs:758-790`），但 `PrepareTrayShowAnimation`（748-751）丢弃布尔结果；仅在拖拽中触发 raise 且 retarget 失败时以暂存 bounds 播放入场动画，窗口极小。
6. `SetAllWidgetsVisibleCoreAsync` 隐藏路径在动画播放前即 `ClearTemporaryRaiseLease`（`WidgetManager.cs:1633`）；若随后动画被中断，临时唤起层需等下一次显式 restore（租约"stays held"语义一致，CancelActiveTrayAnimationsAndRestorePositions 也在每个操作入口重置）。
7. 设计良好点备忘：三个系统事件 watcher 均以字段保活 subclass/Winevent 委托防 GC（`WidgetShowDesktopSelfHealService._winEventProc`、`DisplayAreaWatcherService._messageSubclassProc`、`WidgetDisplayChangeWatcher._subclassProc`）；`DisplayAreaWatcherService` 事件驱动后仍保留 30s 签名轮询兜底；`WidgetPeerOrderMovePlanner` 的 LIS + 自顶向下移动序是正确的最小重排方案；`RestoreGroupPreservingForeground` 对 `HWND_BOTTOM` 与 owner 迁移的旗标区分（`ZOrderRaiseFlags` vs `ZOrderBottomFlags`，`Win32Helper.cs:1704-1718`）与注释一致。

## 4. 小结

- 窗口交互主干（唤起/回落双模式、恢复监视器 + 鼠标采样、租约代际、RaisedBand guest、系统事件三 watcher + 自愈）结构清晰、防御到位，未发现 P0/P1 级缺陷；F7 唤起回落链与 `docs/architecture/[重要勿删]widget_zorder_lifecycle.md` 的现行描述逐点吻合（含坑 #1–#9 的现行对策均在代码中落实）。
- 立案 6 条：P0=0，P1=0，P2=1（FWIN-01，cloak 值掩码语义失同步导致自愈面过窄），P3=5（FWIN-02～06，均为死代码/契约失同步/卫生）。
- 观察项 7 条，其中 4 条与技术手册自述的已知宽判定/有意保留行为相关，已按双盲纪律照实记录、未做已知性推测。
