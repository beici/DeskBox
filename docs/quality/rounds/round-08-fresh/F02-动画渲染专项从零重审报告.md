## 2. 问题清单

### FANI-01 共享 Composition 关键帧动画模板被反复灌入关键帧：无界累积 + 同归一化时刻多值歧义

- 位置：`src/DeskBox/Services/WidgetCompositionResources.cs:32-60`（GetScalar/GetVector3 一次性创建、永久缓存，无关键帧重置）；灌入点：`src/DeskBox/Controls/WidgetShell.xaml.cs:2135-2151`（CompactOpacity，每次过渡每个元素插入 13 帧，一次塌缩最多 9 个元素共用同一模板）、`2161-2177`（CompactScale，25 帧）、`2186-2201`（CompactTranslation，25 帧×2 元素）、`3067-3083`（CompactLiveTranslation/CompactLiveOpacity，每次不定进度条启动 2+17 帧）、`3273-3279`（EdgeGlow，17 帧）、`986-995`（GroupDropBreathing，3 帧）；`src/DeskBox/Services/WidgetTrayAnimationController.cs:421-426/437-442` 与 `540-545/555-560`（TrayOpacity/TrayScale，每次托盘显隐 2 帧）。
- 触发条件：任意一次胶囊展开/塌缩（悬停即触发，本应用最高频动画）、托盘显隐、组拖放预览状态翻转（`WidgetShell.xaml.cs:897-920`，拖动过程中连续触发）、不定进度条因宽度变化重启（`WidgetShell.xaml.cs:3100-3112`）。WinRT `KeyFrameAnimation` 没有关键帧移除 API，模板被反复 InsertKeyFrame 只能累积。
- 风险等级：P2。
- 潜在影响：(a) 每次过渡的 StartAnimation 都会把模板累积的全部关键帧绑定进本次动画，评估与上传成本随会话时长线性增长——长时间运行后胶囊过渡渐现掉帧；(b) 同一归一化时刻存在多套不同元素曲线的关键帧（live/identity/text 三条曲线共用 CompactOpacity 模板），WinRT 对重复时刻语义未定义，若按先插优先评估，第二个元素起会走错缓动曲线（视觉缺陷）；`ResyncCompactTransitionFades`（`WidgetShell.xaml.cs:1933-1947`→`2036`）失障重同步时再灌一套 fromProgress 采样帧，进一步加重。
- 代码层面根因：模板缓存设计（`WidgetCompositionResources` 注释"StartAnimation takes a snapshot of a template"）只对"关键帧固定"的模板成立；粒子路径已经意识到该约束并改用一次性动画（`WidgetShell.xaml.cs:3451-3453`："These animations cannot share the fixed-keyframe templates; release each completed cycle."），但上述固定模板调用点仍在每次启动时灌入可变关键帧。
- 代码证据：
  ```csharp
  // WidgetCompositionResources.cs:37-44 —— 缓存后永不重建、无关键帧清理
  if (_animations.TryGetValue(template, out CompositionAnimation? existing))
  {
      return (ScalarKeyFrameAnimation)existing;
  }
  // WidgetShell.xaml.cs:2140-2149 —— 每次启动向同一模板插入 13 帧
  ```

### FANI-02 自适应降帧阶梯不可达：档位门条件恒真，注释描述的自适应行为从未运行

- 位置：`src/DeskBox/Views/WidgetWindowBase.Collapse.cs:3416-3440`（StartBoundsTransition 档位选择）、`3419`（`if (frameRateCap > 0)`）、`3670-3677`（RecordCollapseAnimationTickCadence 早退）、`127-134`（字段注释宣称的自适应语义）；`src/DeskBox/Services/WidgetCompactFrameSkipPolicy.cs:29-39`（NormalizeFrameRate）、`54-118`（ResolveLevelForFrameRate/ResolveSkip/ShouldEscalate/Escalate 等仅被死分支或纯测试引用）；`src/DeskBox/Models/WidgetShellSettingsSlice.cs:52`（默认 60）；`src/DeskBox/ViewModels/SettingsViewModel.SelectionOptions.cs:89-124`（UI 仅暴露 30/60/90/120 四档，无"自适应/自动"档）。

- 风险等级：P3（行为确定、有默认档位兜底；但属于注释/语义与实现不一致 + 死代码）。
- 潜在影响：`WidgetWindowBase.Collapse.cs:127-133` 与 `WidgetCompactFrameSkipPolicy` 类注释（"Animations start at the display's native rate and escalate one level only when ticks keep overrunning… the achieved level is remembered for the session"）所描述的"默认原生帧率、负载过载才降级、会话内记忆"从未生效；实际默认档位 60 意味着 120/144/165Hz 屏幕上的胶囊形变默认被钉在 ≤60fps，与注释宣称的行为相反。后续维护者按注释排查"高刷机不流畅"问题时会被误导。测试 `CapsuleAnimation_UsesRecoverableSubmissionDeadlinesWithoutSessionDowngrade`（Windows10WidgetMotionContractTests.cs:240-253）仅断言字段名存在，未锚定分支可达性。

### FANI-03 托盘批量动画的 FrameBudget 委托每帧执行 LINQ 管道，与项目自身的"零每帧分配"纪律冲突

### FANI-04 帧回调异常只记日志不注销：持续抛出的回调将以每帧一条的频率刷爆日志

## 3. 观察项（证据不足立案或属设计内权衡，仅记录）

1. `PreArmFrameClock` 悬停预热在无真实动画时持有 `DCompositionBoostCompositorClock` 提升租约最长 5s（`WidgetCompactAnimationCoordinator.cs:158-196`、`PreArmLingerSeconds=5`）。属注释明示的设计权衡（换首帧流畅），但意味着每次掠过胶囊后 DWM 全速空转 5s，对电池敏感场景可观察。
2. `Win32Helper.DisplayTiming.cs:97-102` 用 `(path.Flags & 0x08)` 判定"ModeIndex 高位编码"、`(path.Flags & 0x10)` 判定动态刷新率。这两个魔数与公开的 `DISPLAYCONFIG_PATH_*` 常量（0x08=PreferredSource、0x10=TargetUnion）的对应关系无法在静态审查中确证；若语义不符，`IsDynamic` 判定会影响动态刷新率面板的帧预算取值（取 Max(RefreshRateHz, PhysicalRefreshRateHz)，`WidgetAnimationDisplayTiming.cs:32`）。建议以命名常量落档核实。
3. `WidgetShell.xaml.cs:2906-2908、2926、2936、3023-3026`：胶囊实时进度条/音乐进度条每次呈现更新 `new SolidColorBrush(...)`（项目内已有 `SharedBrushCache`）。音乐播放进度高频更新时为每秒数次的小额分配，量级低。
4. `WidgetShell.xaml.cs:3893-3908` `MeasureCompactTextWidth` 每次跑马灯启动新建 TextBlock 探针测量自然宽度；低频（跑马灯启动时一次），非热路径。
5. `SearchPopupWindow.xaml:599-603、687-691` 两处 `EntranceThemeTransition IsStaggeringEnabled="True"`：搜索结果集较大时逐子项级联入场可能放大首帧成本；搜索面板生命周期短，未立案。
6. `OnboardingWindow.IntroAnimations.cs:29-67` `PlayIntroSequence` 为 `async void`，且 `try` 块之前的 UI 准备段（25-66 行）异常无兜底；首启路径风险低但存在未处理异常面。
7. `WidgetCompactAnimationCoordinator.cs:25` `MaximumConcurrentBoundsTransitions = int.MaxValue` 使 `HasBoundsTransitionCapacity` 恒真，`RegisterBoundsTransition` 的 `InvalidOperationException`（145 行）与 `WidgetCompactAnimationConcurrencyPolicy` 实际不可达；有注释说明系有意放开（避免多胶囊并发被串行化），保留为信息性记录。
8. `WidgetAnimationDisplayTiming.cs:14` 静态 `Monitors` 字典以 HMONITOR 为键，HMONITOR 可被系统复用；因拓扑刷新完成即 `Monitors.Clear()`（`RefreshIfNeeded` 50 行附近）且刷新节流仅 250ms，残留窗口极小，未立案。
9. `App.AotManagedUiSmoke.cs` 等冒烟契约对动画源码做了字符串级锚定（如 `Windows10WidgetMotionContractTests`），对 FANI-02 一类"分支可达性"问题无防护力——契约测试锚定字符串而不锚定行为，后续演化仍可能静默漂移。

## 4. 小结

- 统计：P0 = 0；P1 = 0；P2 = 1（FANI-01）；P3 = 3（FANI-02/03/04）。
- 总体评价：该动画子系统工程质量显著高于常见桌面应用水准——共享帧时钟三源切换（Win11 CompositionTarget.Rendering / Win10 DwmFlush 线程 + 健康熔断 + 显示派生定时器兜底）、引用计数时钟租约、失速钳位时间线、原子化 DeferWindowPos 批提交、paceToDisplay 输入合并、以及大量经证实的每帧分配消除，均有对应注释与契约测试。本轮立案问题集中在两类：一是固定关键帧模板被当作可变模板复用的资源生命周期缺口（FANI-01，长会话渐进劣化）；二是档位/异常兜底等"开关语义"随演化失配留下的死分支与文档漂移（FANI-02/04）。未发现 P0/P1 级失效。
- 建议关注顺序：FANI-01（对长时运行体验有实感影响）→ FANI-02（澄清档位语义并清除死代码/修正注释）→ FANI-04 → FANI-03。
