## 2. 问题清单

### FMEM-01 TodoWidgetStore 静态路径门字典只增不减，备份/恢复的每份暂存路径都会永久沉淀一个门条目

- 位置：`src/DeskBox/Services/TodoWidgetStore.cs:33`（静态字典声明）、`src/DeskBox/Services/TodoWidgetStore.cs:59`（GetOrAdd，全文件无任何 TryRemove/Clear）；放大场景 `src/DeskBox/Services/DeskBoxDataBackupService.cs:490`、`src/DeskBox/Services/DeskBoxDataBackupService.cs:1098`、`src/DeskBox/Services/DeskBoxDataBackupService.cs:1110`、`src/DeskBox/Services/DeskBoxDataBackupService.cs:1515-1516`
- 触发条件：任意创建 `TodoWidgetStore` 的路径（ViewModel、TodoReminderService、SearchEngineService、SearchResultActionService、备份/恢复暂存）都会向静态 `s_pathGates` 以完整 store 路径为键写入一条 `SemaphoreSlim(1,1)`；数据备份/恢复流程在 `RestoreStagingDirectory\<Guid>` 唯一暂存根下为每个 staged widget 构造 store，且从不清理。
- 风险等级：P3
- 潜在影响：进程生命周期内单调增长（每条目约一个 SemaphoreSlim + 键路径字符串，百字节级）。正常使用仅随 widget 增删缓慢累积；执行过多次「作用域恢复」的用户会按「恢复次数 × 暂存 widget 数」加速沉淀。无功能影响，属慢性资源卫生问题。
- 代码层面根因：门字典设计为「按路径共享序列化点」，但缺少与 `GlanceWidgetStore.DeleteForWidgetAsync`（`Services/GlanceWidgetStore.cs:156-162`，widget 删除时 `WidgetStores.TryRemove`）等价的移除机制；对备份暂存这类一次性路径也没有任何回收入口。
- 代码证据摘录：
  - `TodoWidgetStore.cs:33-34`：`private static readonly ConcurrentDictionary<string, SemaphoreSlim> s_pathGates = new(StringComparer.OrdinalIgnoreCase);`
  - `TodoWidgetStore.cs:59`：`_gate = s_pathGates.GetOrAdd(_storePath, static _ => new SemaphoreSlim(1, 1));`（全文件检索无 TryRemove/Clear）
  - `DeskBoxDataBackupService.cs:490`：`stagingRoot = Path.Combine(RestoreStagingDirectory, Guid.NewGuid().ToString("N"));`
  - `DeskBoxDataBackupService.cs:1515-1516`：`var stagedStore = new TodoWidgetStore(stagedWidgetsDirectory, widgetId); var liveStore = new TodoWidgetStore(liveWidgetsDirectory, widgetId);`（stagedWidgetsDirectory 位于上述 Guid 暂存根下）

### FMEM-02 托盘图标外观更新时旧 System.Drawing.Icon 不经应用侧释放，句柄回收完全依赖第三方库与终结器

- 位置：`src/DeskBox/App.Tray.cs:1022`（赋值处）、`src/DeskBox/Helpers/AppBranding.cs:36`（每次新建 Icon）
- 触发条件：主题切换（`ThemeService.AppearanceChanged` → `UpdateTrayIconAppearance`，`App.Tray.cs:226`、`1005-1022`）或用户更改托盘图标样式；每次触发都执行 `_trayIcon.Icon = AppBranding.CreateTrayIcon(...)`，被替换的旧 `System.Drawing.Icon` 在应用代码中无任何 Dispose/持有释放。
- 风险等级：P3
- 潜在影响：每次主题/样式切换最多滞留一个 Icon 对象（内含文件加载的图标数据与惰性创建的 HICON）直至 GC 终结。`System.Drawing.Icon` 实现 IDisposable 并有终结器，最终可回收，故无长期累积；但释放时机不受控，且若 H.NotifyIcon 内部也不释放旧实例（该库仅以 DLL 形式存在，无法从仓库静态核实），句柄滞留窗口期会更长。触发频率低（仅主题变更），影响轻微。
- 代码层面根因：`UpdateTrayIconAppearance` 在覆盖 `_trayIcon.Icon` 前未对旧值调用 `Dispose`，也未保存旧值以便失败时回退释放；`AppBranding.CreateTrayIcon` 每次从磁盘重新 `new Icon(trayIconPath)` 而非复用缓存的两个 ico 资源。
- 代码证据摘录：
  - `App.Tray.cs:1022`：`_trayIcon.Icon = AppBranding.CreateTrayIcon(style, IsDarkThemeActive());`（上下文无旧 Icon 的捕获与释放）
  - `AppBranding.cs:34-38`：`try { return new Icon(trayIconPath); } catch (Exception ex) { ... return null; }`

## 3. 观察项（不计入问题清单）

1. `Helpers/ShellThumbnailProxy.cs:64-65` `s_registeredProviderByExtension` 为无上限静态字典（键为文件扩展名，实际受扩展名全集约束）；与同文件 `s_recentFailures`（`MaximumFailureEntries=256`，第 45 行）的封顶策略不一致，属风格不对称而非现实风险。
2. `Services/PerformanceLogger.cs:258` `s_windowCounts` 为无上限静态字典，但键为窗口种类字符串且仅在 perf logging 启用时写入（`TrackWindowOpen` 第 264 行起），实际有界。
3. `ViewModels/GlanceWidgetViewModel.cs:48、1122-1131` `_onlineRefreshCts` 在 Dispose 与刷新结束路径中只 `Cancel()` 从不 `Dispose()`；无定时器/注册的 CTS 可安全交由 GC，属轻微卫生问题。
4. `Controls/DesktopOrganizationTaskView.Appearance.cs:12-42` 对四个静态/单例服务的退订完全依赖 `Unloaded`；WinUI 3 桌面端窗口销毁时 `Unloaded` 是否必然触发无法从仓库静态核实（同仓库其他窗口均以 `Closed` 为退订点），若不触发则每次打开桌面整理窗口会遗留一组订阅并钉住整个 TaskView 及其预览卡片。建议后续以窗口 Closed 路径兜底（本轮不修改）。
5. `Helpers/IconHelper.cs:1930-1939`（`RecordTimeout`）与 `ShellThumbnailProxy.cs:927-936`（`RecordFailure`）达到条目上限时整体 `Clear()`：内存上有界且封顶，代价是一次性重置全部失败重试抑制，属行为权衡而非泄漏。
6. `Services/WidgetSurfaceSwitchGatePool.cs:30-36` 与 `WidgetSurfaceRegistry.cs:457-460` 在移除会话时刻意不 `Dispose` 门（注释说明为让在途 `Release` 安全），设计自洽，非缺陷。
7. `Views/ContentWidgetWindow.AotNativeDropSmoke.cs:196-341` `AotNativeHDropDataObject` 的 `GlobalAlloc` HDROP 所有权移交 COM medium、`GCHandle`/`NativeMemory` 均在 `Dispose` 配对释放；该类型仅用于 AOT smoke 路径，未发现泄漏。
8. `App.Tray.cs` `TaskbarIcon` 本身无显式 Dispose（进程单例、随应用生命周期存活），无实际泄漏影响。

## 4. 小结

- P0：0 条。未发现生产核心功能失效级别的内存/资源缺陷。
- P1：0 条。未发现高频可复现的资源泄漏；两条工作集回收路径（immediate-hidden、quiescence）的门控、并发去重与冷却逻辑经精读均正确。
- P2：0 条。未发现边界场景下的句柄/GDI/COM 泄漏：全部 AllocHGlobal/AllocCoTaskMem/远程缓冲/进程句柄/DC/ICON 均逐一核对配对；COM 侧 AddRef/Release、PropVariantClear、CoTaskMemFree、ReleaseStgMedium、IL 分配配对完整；Rust 层输出缓冲全部由调用方提供、无跨 ABI 所有权转移，thumbnail-proxy 的低级钩子以 RAII 自解。
- P3：2 条（FMEM-01 TodoWidgetStore 静态门字典慢性无界增长并被备份/恢复暂存路径放大；FMEM-02 托盘图标替换的旧 Icon 依赖终结器回收）。

总体结论：该代码库在内存/资源维度防御密度显著高于常见 WinUI 应用水平——图标/位图/缩略图三层缓存均有容量+字节双预算 LRU 逐出与空闲/隐藏双档释放，所有静态容器（两处例外见问题清单/观察项）均设上限，定时器与事件订阅的退订纪律完整，非托管所有权边界清晰。本轮立案仅 2 条 P3 卫生级问题。
