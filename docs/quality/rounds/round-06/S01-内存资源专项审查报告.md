## 3. 问题清单

> 按风险降序。本轮未发现 P0/P1/P2 级问题；以下两条均为 P3 卫生问题。

### 【MEM-01】托盘图标热替换时旧 `System.Drawing.Icon` 未 Dispose

- 【位置】`src/DeskBox/App.Tray.cs:849-858`（`UpdateTrayIconAppearance`）；`src/DeskBox/App.Tray.cs:129-131`（初始创建）；`src/DeskBox/Helpers/AppBranding.cs:36`（`new Icon(trayIconPath)`）
- 【触发条件】系统深/浅色主题切换（`ThemeService.AppearanceChanged`，`App.Tray.cs:203` 订阅）或托盘图标样式设置变更（`UpdateTrayIcon()` 公开入口，`App.Tray.cs:860-863`）时，执行 `_trayIcon.Icon = AppBranding.CreateTrayIcon(...)`。
- 【风险等级】P3
- 【潜在影响】每次替换丢弃一个持有 GDI HICON 的 `System.Drawing.Icon` 实例且不调用 `Dispose`；该 HICON 只能等待对象终结器回收（`Icon` 拥有自己的句柄，终结时才 `DestroyIcon`）。触发频率为用户级（主题切换/样式切换），单次滞留一个 HICON，量级极小、最终可回收，无持续增长趋势——故定 P3 而非更高。
- 【根因说明】`AppBranding.CreateTrayIcon` 每次调用 `new Icon(trayIconPath)` 返回新实例（`AppBranding.cs:34-37`），调用方将其赋给 `_trayIcon.Icon` 后旧实例引用即刻丢失；`App.Tray.cs` 全文及退出路径（`App.xaml.cs:3721` 仅在进程退出时 `_trayIcon?.Dispose()`）均无对被替换实例的保存/释放逻辑。H.NotifyIcon 的 `TaskbarIcon.Icon` setter 只消费新值，不代管旧实例。
- 【整改建议】在 `UpdateTrayIconAppearance` 中先取出旧值再赋新值并对旧实例调用 `Dispose()`（注意空引用与异常保护），或在 `AppBranding` 增加 `CreateTrayIcon(out Icon previous)` 归还旧实例语义；与 `App.xaml.cs:3721` 退出路径形成一致的显式释放约定。
- 【证据】
  ```csharp
  // App.Tray.cs:849-858
  private void UpdateTrayIconAppearance()
  {
      if (_trayIcon is null) { return; }
      string style = SettingsService.Settings.TrayIconStyle ?? "System";
      _trayIcon.Icon = AppBranding.CreateTrayIcon(style, IsDarkThemeActive());   // 旧 Icon 被直接覆盖丢弃
  }
  // AppBranding.cs:34-37
  try { return new Icon(trayIconPath); }   // 每次新实例，持有 HICON
  ```

### 【MEM-02】瞬态 `SoftwareBitmap` 解码结果未确定性释放（3 处，与既有 `using` 规范不一致）

- 【位置】`src/DeskBox/Services/IQuickCaptureClipboardReader.cs:99` 与 `:124`（`encoder.SetSoftwareBitmap(await decoder.GetSoftwareBitmapAsync())`）；`src/DeskBox/Views/QuickCaptureWidgetWindow.Items.cs:460`（`var softwareBitmap = await decoder.GetSoftwareBitmapAsync();` 后用于 OCR）
- 【触发条件】随记剪贴板监听读取到剪贴板图片（`TryReadBitmapAsPngAsync` / `TryReadStorageFileAsPngAsync`）；用户对随记图片执行"复制图中文字"（OCR）。
- 【风险等级】P3
- 【潜在影响】`SoftwareBitmap` 为 `IDisposable` 的 WinRT 对象，像素数据驻留原生内存（4K 截图约 33MB BGRA）。未 `Dispose` 时依赖 RCW 终结器在下次 GC 后释放，期间原生位图内存滞留。单次操作即逝、无累积，不构成泄漏；但短时高频率图片粘贴/OCR 场景下会抬高瞬时原生内存峰值。
- 【根因说明】同一仓库已确立确定性释放规范：`QuickCaptureService.cs:1763` 使用 `using var softwareBitmap = await decoder.GetSoftwareBitmapAsync(...)`；上述 3 处未遵循。`BitmapEncoder.SetSoftwareBitmap` 不取得所有权（WinRT 语义，调用方负责释放）。
- 【整改建议】统一为 `using var softwareBitmap = await decoder.GetSoftwareBitmapAsync();` 后再交给 encoder/OCR；或在 `encoder.FlushAsync()`/OCR 完成后于 `finally` 中释放。
- 【证据】
  ```csharp
  // IQuickCaptureClipboardReader.cs:96-100（对比 QuickCaptureService.cs:1763 的 using var 写法）
  var encoder = await BitmapEncoder.CreateAsync(BitmapEncoder.PngEncoderId, outputStream);
  encoder.SetSoftwareBitmap(await decoder.GetSoftwareBitmapAsync());   // 临时 SoftwareBitmap 未 Dispose
  await encoder.FlushAsync();
  ```

## 4. 复核确认无问题的重点面（摘要）

以下重点面经逐项核查，**未发现**资源生命周期缺陷（列举供后续轮次免复查）：

1. **Win32/GDI 句柄配对**：`IconHelper` 四条图标提取路径（`TryGetIconFromImageList` 1096-1115、`LoadIconBytesFromShGetFileInfo` 1118-1143、`LoadIndexedIconBytes` 1162-1198、`TryExtractHighResIndexedIcon` 1200-1235）全部 `DestroyIcon` 于 `finally`，`Icon.FromHandle` 包装器经 `using` 释放（`FromHandle` 语义下 `Dispose` 不重复销毁句柄，手动 `DestroyIcon` 是正确且必要的）；`IImageList` RCW 引用计数收支平衡（`SHGetImageList` +1、`GetObjectForIUnknown` +1、显式 `Marshal.Release` −1、RCW 终结 −1）。`FileMetaService.LoadIconBytes:279-295` 同规范。
2. **进程/令牌/跨进程内存**：`App.xaml.cs:449-534`、`DragDropPermissionService.cs:266-930`、`ElevatedFileLauncher.cs:420-439` 的 `AllocHGlobal`/`CloseHandle` 全部 try/finally 配对；`DesktopBlankHitTest.cs:90-160` 的 `VirtualAllocEx`/`VirtualFreeEx`/`FreeHGlobal`/`CloseHandle` 四元组完整。
3. **全局钩子**：`ReservedHotkeyHookService.HookThreadMain` finally 中 `UnhookWindowsHookEx`（`ReservedHotkeyHookService.cs:344`）+ `Stop()` 超时兜底强拆（`:344` 区域），`DesktopDoubleClickActivationService` 同型双保险（`:315`、`:217`）；两服务 `Dispose` → `Stop()` 闭环，且退出序列中先于托盘窗口销毁（`App.xaml.cs:3716-3719` 注释明确该顺序防键卡死）。
4. **OLE 拖放**：`NativeDropTarget` 在 `DragEnter` `Marshal.AddRef` 保留数据对象（`:522-541`），`DragLeave`/`Drop`/`Unregister` 均经 `EndNativeDragVisual → ClearActiveDropDescriptionAndReleaseDataObject`（`:587-589`）配对 `Marshal.Release`，重复 DragEnter 不会覆盖泄漏；窗口关闭时 `RemoveNativeFileDropBridge`（`ContentWidgetWindow.NativeDragDrop.cs:660-688`）解绑事件并 `Dispose` 全部 target。`NativeShellFileDragProvider` 的 PIDL `CoTaskMemFree` 于 finally（`:238-246`），COM 接口指针异常路径也释放（`:233-237`、`SetDataObject` finally `:309-313`）。
5. **缓存有界性总表**：`IconHelper` 三套缓存（图标字节 200 条/32MB、解码位图 160 条/48MB、缩略图 128 条/32MB，均随性能档位缩放且支持空闲折半/清空）；超时表 256 条整体清空；`ShortcutHelper` 元数据缓存 512 条满即清；`FileService` ShellKind 缓存 4096 条 FIFO 淘汰；`FileMetaService` 64 条折半淘汰；`GlanceImagePaletteService` 32 条 LRU；`SharedBrushCache` 512 条满即清；`ShellThumbnailProxy` 失败表 256 条；`GlanceImageService` 磁盘目录 72 项上限并删除陈旧文件；`App.Log` 队列 `MaxQueuedLogLines` 封顶丢弃。**全部有界，无无界增长缓存**。
6. **Timer/Watcher 生命周期**：全部 `DispatcherQueueTimer` 均有 Stop + `Tick -=` 配对（WidgetShell 5 个瞬态 timer 计入 `PerformanceLogger.RecordTransientUiTimerCreated/Released` 对账；ContentWidgetWindow `_autoRestoreTimer`/`_nativeFileDropRegistrationTimer` 在 Closed 释放）；`FolderWatcherService` 双 `FileSystemWatcher` + WinRT 查询三通道在 `Stop()`/`Dispose()` 全量 teardown，且对 `StorageItemQueryResult` 显式 `Marshal.ReleaseComObject`（`:341-346`），重启/重连有代际（generation）防护；`AppDiagnosticsService`/`TodoReminderService`/音乐/天气/Glance VM 均在 Dispose 中停表退订。
7. **AOT/Rust 互操作所有权**：`deskbox_native.dll` 全部导出（shortcut×4、music_volume、explorer_shell_launch、quick_access、recycle_bin）与 C# 侧 backend 均为**调用方固定 UTF-16 缓冲**（`fixed (char* ...)`，`ShortcutNativeBackend.cs:354,447-454,549-554`、`QuickAccessNativeBackend.cs:124-126`、`RecycleBinNativeBackend.cs:88-89`），无跨 ABI 堆分配，不存在"谁释放"歧义；panic 不跨 C ABI（ABI 2 契约）。`EverythingNativeMethods` 结果字符串指针由 SDK 拥有，C# 侧立即 `PtrToStringUni` 拷贝，每次查询前 `Everything_Reset`，退出 `Everything_CleanUp`（`EverythingSearchService.cs:427,584`）。

## 6. 结论

本专项对内存/句柄/缓存/销毁生命周期做了全量关键词扫描与 40+ 核心文件精读。**未发现 P0/P1/P2 级内存资源缺陷**；仓库在缓存有界化（预算 + LRU + 档位缩放）、P/Invoke 异常路径配对释放、钩子/Watcher/Timer 生命周期、AOT 互操作"调用方缓冲"所有权模式上的纪律性显著高于同类 WinUI 项目，且有专门的空闲内存维护与性能对账日志设施支撑 DEF-004 观测。

新立案 2 条，均为 P3 卫生问题：MEM-01（托盘图标热替换旧 Icon 未 Dispose）、MEM-02（3 处瞬态 SoftwareBitmap 未确定性释放）。二者无累积增长趋势，可随任意后续轮次顺手修复。既有观察项（WidgetSurfaceSnapshotCache 死代码、两个未使用字段）复核仍然成立，维持原观察不重复立项；DEF-004 维持"表面高水位、观测中"定位，托管侧未发现可解释其量级的候选泄漏源。
