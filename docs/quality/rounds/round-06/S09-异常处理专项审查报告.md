## 3. 问题清单

### EXC-01【启动链路整体 try 吞失败：任一环节抛出后其余启动步骤静默跳过，用户无感知】
- **位置**：`src/DeskBox/App.xaml.cs:880-1100`（catch 在 1096-1099）
- **触发条件**：OnLaunched 的单一巨型 try 中任一 await 抛出——例如 `WidgetManager.RestoreWidgetsAsync()`（995 行，自带 catch-rethrow 结构，异常继续上抛）、`ManagedStorageDesktopShortcutService.SyncAsync` 之前的任何初始化。
- **风险等级**：P2
- **潜在影响**：异常仅记 `Log("Exception in OnLaunched: …")` 后方法返回。此时 tray 可能已创建（945 行在 restore 之前），应用以"半启动"状态静默常驻：Todo 提醒服务、原生通知服务、更新检查、诊断服务、显示区 watcher、Onboarding、JumpList 全部未启动，且无重试、无用户通知。桌面整理器常驻后台，用户可能数天不重启，功能缺失难以归因。
- **根因说明**：启动步骤串行耦合在一个 try 块内，失败粒度是"整个启动"而非"单个服务"；catch 选择只记日志不反馈，是为防 AOT 崩溃的合理决策，但缺少失败面上报。
- **整改建议**：① 对非关键步骤（更新检查、JumpList、诊断、watcher）各自局部 try，使其失败不阻断后续；② 对关键步骤失败（widget 恢复、设置加载）在 catch 中复用既有通知机制（`ShowSettingsNotification`/`ShowManagedStorageUnavailableNotification` 同款）给出用户可见提示；③ 至少在 catch 中记录"启动终止于哪一阶段"的结构化标记。
- **证据**：
  ```csharp
  // App.xaml.cs:993-1005 —— RestoreWidgetsAsync 失败时清理 deferral 后继续上抛
  try { await WidgetManager.RestoreWidgetsAsync(); }
  catch { if (startupDesktopLayerReadinessTask is not null) { ... } throw; }
  // App.xaml.cs:1096-1099 —— 整体吞掉
  catch (Exception ex) { Log($"Exception in OnLaunched: {ex}"); }
  ```

### EXC-02【未注册 TaskScheduler.UnobservedTaskException / AppDomain 未处理异常：fire-and-forget 异常完全不可见】
- **位置**：全仓库（App.xaml.cs 无注册；grep `UnobservedTaskException`、`AppDomain.CurrentDomain` 于 src/tests/native 均零命中）
- **触发条件**：任何 `_ = Task.Run(...)` / `_ = SomeAsync()` 抛出未被观察的异常（本仓库此类模式大量存在，如 App.xaml.cs:1042 `_ = JumpListService.ConfigureAsync(...)`、1349 `_ = Task.Run(async () => ...)`、1068 `_ = JumpListService.HandleActivationAsync(...)`——后两者内部自吞，但模式本身不保证）。
- **风险等级**：P2
- **潜在影响**：.NET 4.5+ 不再因 UnobservedTaskException 崩溃，因此无崩溃风险；但这些异常的丢失意味着后台任务（如预取、缓存清理、快照）静默失败且零诊断线索，延长缺陷定位周期。
- **根因说明**：兜底矩阵只覆盖了 UI 线程（UnhandledException），漏掉了 GC 终结器线程上浮出的任务异常与 .NET 层 `AppDomain.UnhandledException`（后者还覆盖非 UI 线程的裸异常，是崩溃前的最后记录机会）。
- **整改建议**：在 OnLaunched 中注册 `TaskScheduler.UnobservedTaskException`（记录后 `e.SetObserved()`）与 `AppDomain.CurrentDomain.UnhandledException`（仅记录，用于崩溃前留痕）。纯诊断增强，无行为风险。
- **证据**：`grep -rn "UnobservedTaskException" src tests native` → 零命中。

### EXC-03【OnUnhandledException 无条件 e.Handled = true：破坏态继续运行，无熔断】
- **位置**：`src/DeskBox/App.xaml.cs:3749-3753`
- **触发条件**：UI 线程任何未处理异常（含大量 async void 事件处理器上抛的异常——本仓库 40+ 处 async void handler，见第 4 节移交说明）。
- **风险等级**：P3（设计权衡项；直接崩溃风险被该 handler 压制，但换来状态一致性风险）
- **潜在影响**：常驻整理器不崩是正确取向，但无条件吞掉意味着异常后应用在未知状态下继续运行——布局数据可能半更新、窗口句柄可能半释放；且无连续异常计数，可出现"每秒吞一次异常"的静默劣化循环。
- **根因说明**：兜底 handler 只有"记日志 + 继续"一档，缺少分级。
- **整改建议**：增加滑动窗口计数：短时间连续 N 次未处理异常时升级响应（至少显著告警/考虑受控重启，AOT 下可调用既有 AppRelaunchService 通道）。同时可把 `Log` 升级为带severity 的独立标记行，便于诊断包统计。
- **证据**：
  ```csharp
  private void OnUnhandledException(object sender, Microsoft.UI.Xaml.UnhandledExceptionEventArgs e)
  {
      Log($"Unhandled exception: {e.Exception}");
      e.Handled = true;
  }
  ```

### EXC-05【外部 JSON 时间解析：DateTimeOffset.Parse 包 try 静默降级，无日志无注释】
- **位置**：`src/DeskBox/ViewModels/WeatherWidgetViewModel.DataProcessing.cs:529、542、555、568`（IsDaytimeHour / FormatHourLabel / FormatTime / ParseDateToDayLabel）
- **触发条件**：天气源（MSN/Open-Meteo）返回非 ISO-8601 时间或当前文化下解析失败。
- **风险等级**：P3
- **潜在影响**：不崩溃（catch 返回默认值：白天判定 true / 空标签 / 原样字符串），仅显示劣化且不可归因。
- **根因说明**：外部数据防御正确，但 `Parse+catch` 优于 `TryParse` 的理由不成立；且降级无日志。
- **整改建议**：改 `DateTimeOffset.TryParse` 并保留原降级值；`ParseDateToDayLabel` 处 `DateTimeOffset.Parse(dateStr)` 未指定 culture（ISO 8601 建议传 `CultureInfo.InvariantCulture` 或 `DateTimeStyles.RoundtripKind`）。
- **证据**：
  ```csharp
  private static bool IsDaytimeHour(string isoTime)
  {
      try { var dt = DateTimeOffset.Parse(isoTime); return dt.Hour >= 6 && dt.Hour < 19; }
      catch { return true; }
  }
  ```

## 4. 正面确认（未立案，作为审查基线记录）

### 4.1 FileService 传输链路的异常纪律（正面）
- 复制失败先清理半写目标再 `throw`（FileService.cs:2002-2012、TransferProgress.cs:387-394）；目录复制失败回滚已完成子操作后重抛（FileService.cs:2252-2262、TransferProgress.cs:546）。
- CaseOnlyRename 具备完整的两段回滚（失败聚合为 AggregateException 重抛，FileService.CaseOnlyRename.cs:38-65）。
- 1875 行 `catch { return true; }` 是 fail-closed 设计（无法判定时按"同目录=危险"处理），语义正确。

### 4.2 外部输入面防护（正面）
- **WeatherService**：HTTP/JSON 全部在 `FetchFromSourceAsync` 分级 catch（取消例外 rethrow）→ 源失败自动切换备用源 → 双失败回退 stale 缓存；缓存 `WeatherCacheStore.LoadCoreAsync` 自吞损坏 JSON 返回默认态（无故障任务缓存问题——`_cacheLoadTask` 只会成功完成）。
- **EverythingSearchService**：DllNotFound/BadImageFormat/EntryPointNotFound/IPC 错误逐级分类为状态快照，查询失败返回空页不崩溃。
- **CitySearchService.SearchAsync**：API 失败降级为纯本地结果。
- **MarkdownInlineImageExtractor**：Base64 `FormatException` 吞掉跳过（合理）、保存失败日志后跳过、20MB/50MB 上限防爆炸。
- **MarkdownEditCommandEngine**：所有 selectionStart/Length 入口 `Math.Clamp`，Substring 不可越界。
- **AccentColorHelper**：hex 长度预校验（6/8），非法字符 FormatException 被 catch 返回 false——合理降级。
- **JumpListService**：ConfigureAsync/HandleActivationAsync/EnsureShortcutAumid 全量 try + 日志；HandleActivationAsync 以 `_ =` 调用但内部自吞，安全。
- **ManagedStorageDesktopShortcutService.SyncAsync**：整体 catch + 日志（注释明确"不得阻断启动"）。

### 4.3 Rust FFI 边界（正面）
- **无 panic 跨 C ABI 风险**：`native/deskbox-native/src/lib.rs` 全部 23 处 `unwrap/expect` 位于 1432 行起的 `#[cfg(test)]` 模块；五个生产模块（shortcut/music_volume/quick_access/recycle_bin/explorer_shell_launch）grep 零命中 `unwrap()/expect()/panic!`。全 crate 无 `catch_unwind`（也不需要——生产路径无 panic 源）。thumbnail-proxy 的 panic 同样全部位于 `#[cfg(test)]`（main.rs:665 起）。
- **FFI 错误码被双向校验**：C# 侧 ShortcutNativeBackend（379/387/485/493/602/611）、MusicVolumeNativeBackend（167/177/194）、RecycleBinNativeBackend（109/120/141）均校验 `返回值 == result.Status` 的一致性并区分 StatusOk/OperationSucceeded，无忽略返回值的调用。

### 4.4 崩溃数据保护（正面）
- settings.json 经 `ResilientJsonStore` 保存：临时文件 + `File.Replace`（带 .bak 备份）原子替换，替换失败重试两次后仅在"双文件完整"不变量成立时走受控非原子回退（ResilientJsonStore.cs:120-210）；读取侧主文件损坏即隔离（Quarantine）并自动从 .bak 恢复，恢复失败亦不会令有效备份"看起来全部丢失"。
- 启动时 `ApplyPendingRestoreAsync` + `CreateAutomaticSnapshotIfDueAsync`（App.xaml.cs:908-914）；设置加载失败有 `LastLoadRecoveryState` + 恢复快照通知；桌面整理事务有 journal 恢复（`RecoverPendingAsync`）。崩溃半写窗口被覆盖。

### 4.5 剪贴板监听（正面）
- `QuickCaptureClipboardService.CaptureCurrentClipboardAsync` 全路径 try/catch：失败置诊断原因 `failed:read-or-save` 并记日志（QuickCaptureClipboardService.cs:240-244）；`_isProcessing/_hasPendingCapture` 防重入；`ImagePngBytes!`/`Text!` null-forgiving 有 `HasImage`/`IsNullOrWhiteSpace` 前置判空，即使模型不一致也落入外层 catch 不崩溃。TodoClipboardFormatter 为纯格式化无异常面。

### 4.6 async void 异常可见性（记录）
- 全仓 40+ 处 `async void`（去 Smoke 后约 35 处，主要集中 FileSurfaceContent/MusicWidgetContent/ContentWidgetWindow 事件处理器）。异常可见性结论：均沿 SynchronizationContext 浮至 `Application.UnhandledException`，被 EXC-03 handler 记录（有日志、不崩溃、无熔断）。FileSurfaceContent 的 handler 经 `RunAsync` 包装（局部 try），Music/Content 类直接 await ViewModel（依赖全局兜底）。详见第 5 节移交第 1 条。

## 5. 跨界移交

1. **线程安全专项**：本仓库 40+ 处 `async void` 事件处理器（列表见扫描记录，典型如 MusicWidgetContent.xaml.cs:113-150、FileSurfaceContent.xaml.cs:646-3678）——其中异常**可见性**现状：async void 异常会沿 SynchronizationContext 浮至 `Application.UnhandledException` 被 EXC-03 的 handler 记录，不崩溃。但 async void 中的重入/竞态面（如 drag/drop deferral、双击竞态）归线程安全专项；本报告不重复立案。
2. **资源管理专项**：EXC-01 中"半启动状态未释放已创建资源"的资源维度（如 tray 已创建但后续失败时的清理路径）值得资源专项复核。
3. **本地化专项**：EXC-05 的 `ParseDateToDayLabel` 文化映射 switch 硬编码 12 语言键，新增语言需同步维护（本地化覆盖专项已有关注点）。

## 6. 结论

- 确认问题 **6 条**：P2 × 2（EXC-01 启动失败静默、EXC-02 UnobservedTaskException 缺失），P3 × 4（EXC-03 无熔断吞兜底、EXC-04 吞异常卫生项清单、EXC-05 天气时间解析、EXC-06 城市库 getter）。**未发现 P0/P1 级异常处理缺陷**。
- 未发现"崩风险吞"（该抛而吞导致数据丢失/崩溃扩大的场景）；空 catch 全部定性为合理降级或卫生改进。
- Rust 边界、FFI 错误码、文件传输回滚、崩溃数据保护均为正面确认项。
- 覆盖率限制：`!` null-forgiving 与 40+ async void 处理器为抽查而非全量；Views/ViewModels 层异常分支以关键词扫描覆盖，未逐行精读。
