## 2. 已有功能复核

### 2.1 BATCH2-F1 格子边距手动精确输入 —— 常规路径正确，批量路径存在 3 处缺陷（见 LAY-01/02/07、LAY-03）

代码级复核结论：

- **输入拦截**：`WidgetMarginSettings.TryParseMargin`（`WidgetTitleAppearanceSettings.cs:164-167`）用 `int.TryParse + [0,200]` 区间判断，负数、>200、非数字、空串均被拒绝；`TryPreview` 对非法输入只显示校验文案不应用（`WidgetWindowBase.TitleAppearance.cs:275-296`）。正确。
- **实时预览**：`TryPreview → ApplyMarginsFromDialog` 每次有效编辑即移动窗口，所见即所得。正确。
- **取消恢复**：对话框打开时用 `GetWindowRect` 捕获 `dialogInitialRect`（物理 4 元组：Left/Top/宽/高），取消时逐一比较后 `SetWindowPos` 复原，并补 `CapturePositionAnchor + UpdateConfigBoundsFromPhysical(persist:true)`（`TitleAppearance.cs:308-347`）。恢复精确且锚点一致。正确。
- **双向同步**：距离值不落盘，每次打开对话框与每次应用后均从活动窗口 rect 实时派生（`GetCurrentWorkAreaMargins`，`TitleAppearance.cs:429-435, 478-501`），仅持久化"统一/分边"入口模式（`WidgetMarginSettings.ModeOverrideMetadataKey`）。拖动后数值必然一致。正确。
- **随布局持久化**：单窗口路径 `ApplyOwnMarginDelta` → `CapturePositionAnchor` + `UpdateConfigBoundsFromPhysical(persist:true)`（`TitleAppearance.cs:466-475`），锚点、坐标、版本一致更新。正确。
- **批量应用**：存在 LAY-01（锚点不刷新→重启回退）、LAY-07（批量绕过位置锁）、LAY-02（无屏幕 clamp）与 P3 卫生项（每次 TextChanged 对全部可见窗口执行移动+逐窗持久化，无防抖；注释声明批量模式"立即生效、取消不恢复其他窗口"为设计决定，`TitleAppearance.cs:304-307`）。

### 2.2 BATCH2-F3 标题对齐 / 自定义图标 / 组内标题排序 —— 未发现缺陷

### 【LAY-01】批量边距应用移动窗口后不刷新位置锚点与组布局，重启/拓扑切换后批量移动整体回退

- 【位置】`src/DeskBox/Services/WidgetManager.BulkAppearance.cs:67-84`（`MoveVisibleWidgets`）；触发链 `src/DeskBox/Views/WidgetWindowBase.TitleAppearance.cs:401,418`（边距对话框"应用到所有"分支）
- 【触发条件】边距对话框勾选"应用到所有格子"并保存/预览（批量分支对**包括源窗口在内**的所有可见窗口执行 `MoveVisibleWidgets`），之后重启应用或发生显示器拓扑切换。
- 【风险等级】P1（已交付功能 BATCH2-F1 批量模式的核心承诺"随布局持久化"在该模式下失效；100% 可复现）
- 【潜在影响】下次启动时 `NormalizeWidgetBounds → ResolveBoundsForCurrentTopology` 因 `HasValidAnchor` 为真而**忽略已更新的 X/Y**、按旧 `PositionAnchor/PositionMarginX/Y` 重建位置（`WidgetPositioningService.ResolveBoundsCore`，`WidgetPositioningService.cs:80-89`），所有被批量移动的窗口回到旧位置；拓扑切换时 `WidgetTopologyLayoutService.ApplyProfile` 同样按旧锚点投影。若被移动的是组宿主，`WidgetGroupConfig.X/Y` 也未同步（`SynchronizeGroupLayoutFromMember` 未调用），组的拓扑 profile 将持久化旧布局，影响全部成员。
- 【根因说明】`MoveVisibleWidgets` 只调用 `SetWindowPos + UpdateConfigFromPhysicalBounds`（后者仅写 X/Y/Width/Height/坐标版本，`WidgetPositioningService.cs:245-257`），既不调用 `CaptureAnchor`，也不同步组布局；而窗口自身的 `OnAppWindowChanged` 在非拖拽状态下早退（`WidgetWindowBase.Bounds.cs:602-609`），不会补采锚点。对比单窗口路径 `ApplyOwnMarginDelta` 明确调用了 `CapturePositionAnchor`（`TitleAppearance.cs:474`），证明这是批量路径的遗漏而非约定。`WidgetManager.cs:2421-2433` 的 `shouldCaptureAnchor` 在创建窗口时从锚点解析结果重采锚点，只会把旧位置"固化"，无法挽回。
- 【整改建议】在 `MoveVisibleWidgets` 的成功分支中，对 `window.Config` 调用与单窗口路径相同的锚点捕获（等价于 `CapturePositionAnchor(target...)` 的逻辑，注意复用 `UpdateConfigFromPhysicalBounds` 已选出的 workArea），并当该窗口属于组时调用 `SynchronizeGroupLayoutFromMember`；或让批量路径复用 `WidgetWindowBase.ApplyWindowBounds(persist:true)` 的既有链路。

### 【LAY-03】边距对话框目标坐标不做工作区 clamp，可把格子推出屏幕；per-side 过约束时静默取一边

- 【位置】`src/DeskBox/Views/WidgetWindowBase.TitleAppearance.cs:516-578`（`ShiftBoundsToMargins`）、`:584-627`（`ShiftBoundsToNearestEdge`）；消费方 `ApplyOwnMarginDelta`（`:466-475`）与 `MoveVisibleWidgets` 均不 clamp
- 【触发条件】格子宽度/高度接近工作区（例如 `width > workArea.Width - 2×200`）时输入较大边距；或 per-side 输入的两侧距离之和不满足 `left+width+right ≤ workArea.Width`。
- 【风险等级】P2（边界场景；小屏/大格子可复现）
- 【潜在影响】格子被移出工作区一部分（对话框显示值与实际落点不一致）；下次启动 `ResolveBoundsCore → EnsureVisible` 又把格子拉回工作区（`WidgetPositioningService.cs:259-283`），位置再次漂移。另：per-side 分支 `Math.Abs(left - currentLeft) <= Math.Abs(right - currentRight)` 的 tie-break 在两侧等距时静默优先左/上，过约束输入的另一半被无声忽略。
- 【根因说明】对话框链路是唯一不经过 `EnsureVisible` 的落点计算（其余摆放路径均调用：`InitialFileWidgetPlacementPolicy.cs:34`、`ResolveBoundsCore`、`ResolveLegacyPhysicalBounds`）。
- 【整改建议】对计算出的 `newX/newY` 结果套用 `WidgetPositioningService.EnsureVisible(target, workArea)`；per-side 过约束时提示或按输入侧优先级显式说明。

### 【LAY-04】胶囊排列在极小工作区无法收敛时溢出，且组级 clamp 只做单向补偿

- 【位置】`src/DeskBox/Services/WidgetCapsuleArrangementCalculator.cs:155-193`（`FitPrimarySizes` 收尾循环）、`:196-229`（`ClampGroupIntoWorkArea`）
- 【触发条件】胶囊数量 × 最小尺寸(1px) + spacing > 工作区长度（极小屏/虚拟机分辨率 + 大量胶囊），此时所有 item 已降到 1px 仍 `excess > 0`，`while` 因 `sizes[index] <= 1` 全部 continue 而 `break`，总宽/高仍超可用长度。
- 【风险等级】P2（明确边界场景，正常桌面分辨率不会触发）
- 【潜在影响】整条胶囊栏溢出；`ClampGroupIntoWorkArea` 对 `minX < workArea.X` 与 `maxX > workRight` 只修一个方向（if/else if），双向越界时仅保证贴一侧，另一侧仍出屏。
- 【根因说明】`FitPrimarySizes` 的最小值下限是 1 而非"可容纳数量上限"；数量本身未按可用长度截断。
- 【整改建议】在 `Calculate` 入口按 `availableForItems` 截断可排数量（溢出部分留在自由摆放），或对溢出结果记录日志并在 UI 提示。
- 【证据】

```csharp
// WidgetCapsuleArrangementCalculator.cs:164-184
int excess = sizes.Sum() - availableForItems;
while (excess > 0)
{
    bool reduced = false;
    for (int index = sizes.Length - 1; index >= 0 && excess > 0; index--)
    {
        if (sizes[index] <= 1) { continue; }   // 全部为 1 时无路可减
        sizes[index]--; excess--; reduced = true;
    }
    if (!reduced) { break; }                    // 仍 excess>0，静默溢出
}
```

- 【风险等级】P3（不崩溃：`ResolveBoundsCore` 中 `(int)Math.Round(NaN)` 经 unchecked 转换归 0（.NET 定义行为），位置回原点而非异常；成员经 `ApplyGroupLayoutToMember` 继承同样坐标）
- 【潜在影响】损坏的组坐标归零后经 `CaptureGroupLayout` 反向"固化"，原布局信息丢失。

## 4. 跨界移交（配置持久化专项）

- `WidgetConfig/WidgetGroupConfig` 的坐标系契约（X/Y 物理像素、Width/Height 逻辑像素、`BoundsCoordinateVersion` 迁移）是布局正确性的隐式前提，其 JSON 反序列化对 `NaN/Infinity` 数值的接受性、以及损坏文件的恢复策略，建议移交配置持久化专项核查（与 LAY-07 的消费侧防御互补）；布局数据结构本身（`WidgetTopologyLayoutProfile` 上限 12 份裁剪、`RemoveStaleSurfaces`）在本专项内未见缺陷。

## 5. 结论

本专项对格子布局全链路（定位/吸附/胶囊排列/自动摆放/组管理/拖拽落点/持久化恢复）完成了代码级审查，共立案 **7 个问题：P1×1、P2×3、P3×3**，无 P0。核心计算服务（`WidgetSnapCalculator`、`WidgetCapsuleArrangementCalculator` 常规路径、`WidgetTopologyLayoutService`、`ReorderDropIndexCalculator`、`WidgetGroupOrder`、`WidgetGroupSettings.Normalize`、`WidgetCompactBoundsCalculator`、`StackPopoverLayoutCalculator`）逻辑严密、边界处理成熟，未发现除零/负宽/错序类缺陷。BATCH2-F1 单窗口链路与 BATCH2-F3、DEF-006 修复均复核通过。唯一 P1（LAY-01）集中于 BATCH2-F1 批量应用路径：批量移动不刷新锚点导致重启后回退，且该路径同时缺失位置锁检查（LAY-02）与屏幕 clamp（LAY-03），建议作为一个修复包在下一轮闭环。
