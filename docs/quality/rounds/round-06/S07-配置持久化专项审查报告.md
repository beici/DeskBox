## 2. 已有项复核

### 2.1 BATCH2-F1 边距持久化链路

**总体结论：单格链路健壮、读写对称；批量（应用到全部）路径存在 2 个内部缺陷（CFG-01、CFG-02，见 §3）。不重复立项，仅挖内部缺陷。**

已验证的健全部分：

- 距离值不二次存储：对话框每次打开从活动窗口 bounds 实时推导（`WidgetWindowBase.TitleAppearance.cs:213` 起的 `GetCurrentWorkAreaMargins`），拖拽与录入天然双向同步；唯一落盘的新增项是录入模式偏好 `WidgetConfig.Metadata["WidgetMarginEntryMode"]`（`WidgetTitleAppearanceSettings.cs:125`），旧配置文件免迁移兼容，符合设计文档。
- 0–200 拦截双侧一致：`TryParseMargin`（`WidgetTitleAppearanceSettings.cs:164`）在 `TextChanged` 预览（`TitleAppearance.cs:296`）与保存校验（`TitleAppearance.cs:393-402`）使用同一函数；`ApplyMarginsFromDialog` 再次独立解析，无旁路。
- 取消恢复链路完整：对话框记录 `dialogInitialRect`，取消时若窗口已被预览移动则 `SetWindowPos` 复原并调用 `CapturePositionAnchor` + `UpdateConfigBoundsFromPhysical(persist: true)`（`TitleAppearance.cs:337-345`）——恢复也走持久化链路，不会留下"界面复原、配置未复原"的漂移。
- 保存链路：`SetModeOverride`（默认模式删除键，无脏数据）→ `UpdateWidget`（尊重 `DeletedWidgetIds`，`SettingsService.cs:999-1015`）→ `SaveDebounced`（1s 防抖 + `_fileWriteLock` 串行 + `ResilientJsonStore` temp+replace+`.bak`）。单格路径 `ApplyOwnMarginDelta` 先 `CapturePositionAnchor` 再 `UpdateConfigBoundsFromPhysical(persist:true)`（`TitleAppearance.cs:474-475`），与拖拽结束路径（`WidgetWindowBase.Interaction.cs:405-406`）完全同构。
- 批量路径 `MoveVisibleWidgets`（`WidgetManager.BulkAppearance.cs:37-93`）对每个窗口 `UpdateWidget(notify:false)` 后统一一次 `SaveDebounced(notify:false)`，写放大受控——但存在 §3 的 CFG-01/CFG-02。
- 位置锁定一致性：单格路径 `ApplyOwnMarginDelta` 对 `Config.IsPositionLocked` 直接返回（`TitleAppearance.cs:442-447`），与拖拽路径同策略；批量路径对锁定格子未显式豁免（锁定格子的 bounds 也会被 transform 后 `SetWindowPos` 移动）——因批量路径本身即"显式批量操作"，与标题对齐批量操作同语义，不计缺陷，仅提示。

### 2.2 AOT 序列化 smoke 对照

**结论：全仓未发现反射序列化残留；smoke 与真实存储实现对应关系成立。**

- `JsonSerializable` 覆盖 26 个 `JsonSerializerContext`（12 个 App.Aot* smoke 专用 + 14 个生产上下文：SettingsJsonContext、TodoJsonContext、QuickCaptureJsonContext、GlancePreferencesJsonContext、BackupJsonContext、AppUpdateJsonContext、WeatherJsonContext、SearchHistoryJsonContext、LocalizationJsonContext、GlanceImageCatalogJsonContext、DesktopRecoveryJsonContext、NativeNotificationActivationEnvelopeJsonContext、WidgetMetadataJsonContext、DiagnosticsJsonContext）。
- 全部 `JsonSourceGenerationOptions` 均为 `JsonSourceGenerationMode.Metadata`（允许运行期自定义 options，`DeskBoxDataBackupService.CreateDataJsonOptions` 的用法 AOT 安全）。
- 全仓 `JsonSerializer.Serialize/Deserialize` 调用点逐一核对第二参数，全部传入 `JsonTypeInfo`/`*JsonContext.Default.*`；唯一的 `new JsonSerializerOptions` 出现在测试工程（`tests/DeskBox.Tests/DeskBoxDataBackupServiceTests.cs:261,331`），不进 AOT 产物。
- enum 序列化双保险：生产上下文多带 `UseStringEnumConverter`，`WidgetKind` 自定义 `WidgetKindJsonConverter`（`WidgetConfig.cs:245`）对未知值回退 `File` 且 `Enum.IsDefined` 防御，AOT 下无反射枚举转换。
- smoke ↔ 真实实现对照：`App.AotGlancePersistenceSmoke.cs:152`→`GlanceWidgetStore`（真实 Store）；`App.AotQuickCapturePersistenceSmoke.cs:41,155`→`QuickCaptureService.GetDataAsync()`（真实 Store 链）；`App.AotTodoAttachmentsPersistenceSmoke.cs:44`→`new TodoWidgetStore(...)`（真实 Store）；`WidgetManager.AotWeatherSettingsPersistenceSmoke.cs`→`WeatherWidgetViewModeSettings` metadata 读写 + App 层 `FlushPendingSaveAsync`→`SettingsService` 真实落盘；`WidgetManager.AotPersistenceSmoke.cs`→`SettingsService.UpdateWidget` + 边界捕获真实链路。smoke 不是平行实现，是对生产序列化面的真实驱动。

### 2.3 数据丢失风险面复核（未发现 P0/P1 级问题）

- **损坏恢复**：`ResilientJsonStore.LoadWithResultAsync` 主文件解析失败先隔离为 `*.corrupt-时间戳-GUID`（不删除用户数据），再读 `.bak`，备份恢复成功后尝试写回主文件且失败不视为总损失（`ResilientJsonStore.cs:46-114`）。**未发现"反序列化失败→默认值覆盖写回"导致数据丢失的路径**；`SettingsService.LoadAsync` 在 `DefaultsAfterFailure` 时强制 `HasResolvedInitialFileWidgetSetup=true`，防止凭空制造新 widget（`SettingsService.cs:686-701`）。
- **写入原子性**：主链路 temp（GUID 名）→ `File.Replace`（带 `.bak`）→ 失败重试 2 次 → `ERROR_UNABLE_TO_REMOVE_REPLACED` 专属回退（先验证备份逐字节可读，再 WriteThrough 原位写，`ResilientJsonStore.cs:226-254`）。设计完备。
- **并发写**：SettingsService `_fileWriteLock` + 防抖；WeatherCacheStore per-path `SemaphoreSlim`；GlanceWidgetStore per-instance gate + `ConcurrentDictionary` 单例；QuickCaptureService `_gate`；BackupService `_gate` 全方法串行。TodoWidgetStore 例外（CFG-09，P3）。
- **退出 flush**：`App.xaml.cs:1321 FlushSettingsForEndSession`（3 秒上限等待）+ 退出序列 `WidgetManager.CloseAll()`（先释放 surface 允许其提交最后一次快照）后无条件 `FlushPendingSaveAsync`（`App.xaml.cs:3706`）；`HasPendingSave` 仅诊断包消费，退出 flush 不依赖该标志，无漏 flush 风险。
- **路径容错**：数据根来自 `Environment.GetFolderPath(LocalApplicationData)` / `UserProfile` API，天然兼容中文/空格/OneDrive 重定向；`ResilientJsonStore` 临时文件用 GUID 命名，无用户输入进文件名；`WidgetFileStackSettings`/`TodoWidgetStore`/`GlanceWidgetStore` 对 widgetId 做 `Path.GetInvalidFileNameChars` 消毒。恢复快照目录刻意放在数据根之外（`DeskBoxDataPathService.cs:41-45`），卸载不清除恢复副本。

- 12 个文件键集完全一致：每文件 **2545** 键；两两差集 **缺失=0、多余=0**；格式占位符差异 **0**。AGENTS.md 的键/占位符一致性强约束当前满足。

## 3. 问题清单（风险降序）

### 【CFG-01】批量边距（应用到全部）持久化遗漏锚点捕获，重启后布局回退

- 【位置】`src/DeskBox/Services/WidgetManager.BulkAppearance.cs:83-91`（`MoveVisibleWidgets`）；对照单格路径 `src/DeskBox/Views/WidgetWindowBase.TitleAppearance.cs:474-475`
- 【触发条件】用户在边距对话框勾选"应用到全部"并保存/预览，任一被移动格子存在有效锚点（`PositionAnchor` 非空，任何被拖拽过或创建时定位过的格子均满足），随后重启应用、显示器拓扑变化或窗口重建触发 `ResolveBounds*` 恢复。
- 【风险等级】**P2**（批量入口 + 持久化后静默回退，可稳定复现；单格路径不受影响，故非 P1）
- 【潜在影响】被批量移动格子的持久化 `X/Y` 已更新，但 `PositionAnchor/PositionMarginX/PositionMarginY/PositionMonitorKey` 保持移动前旧值；恢复路径 `WidgetPositioningService.ResolveBoundsCore:83` 在 `HasValidAnchor(config)` 时**优先用锚点边距、忽略 X/Y**，因此重启后格子回到批量移动前的旧边距位置——批量边距操作在会话间不生效。
- 【根因说明】批量路径只调用了 `UpdateConfigFromPhysicalBounds`（仅写 X/Y/Width/Height，`WidgetPositioningService.cs:245-257`），没有调用单格路径使用的 `CapturePositionAnchor`（锚点+边距+监视器簿记，`WidgetWindowBase.Bounds.cs:499-529`），两条持久化路径不对称。
- 【整改建议】在 `MoveVisibleWidgets` 中，对非压缩态窗口在 `UpdateConfigFromPhysicalBounds` 之前补充与单格路径一致的锚点捕获（可复用窗口侧 `CapturePositionAnchor` 语义或在 BulkAppearance 内对 Config 调 `WidgetPositioningService.CaptureAnchor`）；补一条"批量边距→重启→位置保持"的回归用例。
- 【证据】
  ```csharp
  // WidgetManager.BulkAppearance.cs:83-84 —— 无 CapturePositionAnchor
  WidgetPositioningService.UpdateConfigFromPhysicalBounds(window.Config, target, workArea);
  _settingsService.UpdateWidget(window.Config, notifySubscribers: false);
  // WidgetWindowBase.TitleAppearance.cs:474-475 —— 单格路径两步都有
  CapturePositionAnchor(next.X, next.Y, next.Width, next.Height);
  UpdateConfigBoundsFromPhysical(next.X, next.Y, next.Width, next.Height, persist: true);
  // WidgetPositioningService.cs:83-87 —— 恢复时锚点优先于 X/Y
  if (HasValidAnchor(config)) { x = ResolveAnchoredX(...); y = ResolveAnchoredY(...); }
  ```

### 【CFG-02】批量边距对压缩态（胶囊）格子无守卫，胶囊几何覆盖展开态持久化字段

- 【位置】`src/DeskBox/Services/WidgetManager.BulkAppearance.cs:37-93`；对照窗口自身守卫 `src/DeskBox/Views/ContentWidgetWindow.xaml.cs:555-583`、`src/DeskBox/Views/WidgetWindowBase.Bounds.cs:508-512`
- 【触发条件】批量边距执行时，任一可见格子正处于压缩/胶囊态（`IsCompactBoundsStateActive = IsWidgetCollapsedBoundsActive || _targetCollapsed`，`WidgetWindowBase.Collapse.cs:193`）。
- 【风险等级】**P2**（依赖"批量操作时存在塌缩格子"这一前置状态；后果是持久化数据被污染，重启后可见）
- 【潜在影响】`MoveVisibleWidgets` 对胶囊窗口直接 `SetWindowPos` + `UpdateConfigFromPhysicalBounds(window.Config, 胶囊bounds, …)`，把胶囊的物理 bounds 写入展开态的 `Config.X/Y/Width/Height`；而窗口自身的持久化路径在该状态下会改走 `CaptureCompactPlacement`（`Bounds.cs:508-512`）且不覆盖展开字段（`ContentWidgetWindow.xaml.cs:562-571`），`CompactPlacement` 在批量路径下完全未被更新。重启后该格子展开几何以胶囊尺寸/位置恢复（`ResolveWidgetBoundsForCurrentState` → `ResolveBoundsForCurrentTopology(Config)`，`WidgetWindowBase.Collapse.cs:3561-3574`），展开态布局被破坏且难以手动察觉来源。
- 【根因说明】`MoveVisibleWidgets` 绕过了窗口层 `UpdateConfigBoundsFromPhysical` 的全部状态守卫（压缩态、显示拓扑迁移 `CanPersistBoundsChange`），直接操作 Config；批量辅助函数只考虑了几何变换，未复刻窗口层的持久化前置条件。
- 【整改建议】批量路径对 `IsCompactBoundsStateActive` 窗口跳过或改走窗口侧 `UpdateConfigBoundsFromPhysical`/`CaptureCompactPlacement` 通道；同时评估与 CFG-01 一并补齐锚点捕获。
- 【证据】
  ```csharp
  // ContentWidgetWindow.xaml.cs:561-571 —— 窗口自身路径：压缩态只落 CompactPlacement，不碰展开字段
  if (IsCompactBoundsStateActive) {
      if (persist) { SettingsService.UpdateWidget(_config, ...); SettingsService.SaveDebounced(...); }
      return;
  }
  // WidgetManager.BulkAppearance.cs:83 —— 批量路径无任何状态分支，直接写 Config
  WidgetPositioningService.UpdateConfigFromPhysicalBounds(window.Config, target, workArea);
  ```

### 【CFG-05】设置迁移管道单步失败仍推进 SchemaVersion，失败迁移被永久跳过

- 【位置】`src/DeskBox/Services/SettingsMigrationService.cs:56-75`（`RunMigrations`）

## 5. 结论

配置持久化主链路质量高：`ResilientJsonStore` 的 temp+replace+`.bak`+损坏隔离+验证式原位回退构成完整的数据保护层，`SettingsService` 的防抖/串行写/退出 flush/恢复态标记（`HasResolvedInitialFileWidgetSetup` 防凭空建格）覆盖了主要数据丢失场景；迁移管道版本化清晰；AOT 序列化面全量 context 化、无反射残留，且 smoke 直接驱动真实 Store；十二语言 JSON 键与占位符完全一致。

本轮发现 **9 项问题：P0×0、P1×0、P2×2（CFG-01 批量边距锚点缺失致重启回退、CFG-02 批量边距污染压缩态格子持久化字段）、P3×7**。两项 P2 均集中在 BATCH2-F1 的"应用到全部"批量持久化路径（单格路径健全），属于该功能持久化链路的内部缺陷，不推翻 BATCH2-F1 的既有闭环结论。数据丢失风险面（默认值覆盖写回、并发写、退出 flush、Suspending）复核未发现 P0/P1 级问题。
