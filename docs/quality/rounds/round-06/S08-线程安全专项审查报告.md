## 2. 已知问题复核：DEF-001 dispatcher 线程注册修复链路

**结论：现实现完备，无残留缺陷，不重复立项。**

DEF-001 曾修的"dispatcher 线程注册"问题现由三道防线组成，逐一复核：

1. **注册线程保证**（`Services/WidgetShowDesktopSelfHealService.cs:47-67`）：`Start()` 判断 `HasThreadAccess`，不在 dispatcher 线程时 `TryEnqueue(StartCore)`。注释明确记录了 R1 修复的根因：*"async startup continuation that constructs this service can resume on a thread-pool thread, where the hook would register successfully yet never receive a single event"*。`WINEVENT_OUTOFCONTEXT` 钩子由 dispatcher 消息循环（UI 线程）拥有。
2. **回调投递链**（同文件 `WinEventCallback` L99-117）：out-of-context WinEvent 回调本身即送达 UI 线程消息循环，回调内只做 `_debounceTimer.Stop()/Start()`（L114 注释："only restart the debounce here, never touch widget state"），验证动作经 `DispatcherQueueTimer.Tick → DebounceTimer_Tick → _verifyAction`，全部在 UI 线程执行。**无漏投递点。**
3. **验证动作线程核对**：`_verifyAction` 即 `WidgetManager.VerifyRestingWidgetsAfterShellMinimize`（`WidgetManager.ShowDesktop.cs:26`），内部只触碰窗口句柄（`Win32Helper`）与 WidgetManager 自身 UI 线程字段，调用方（`App.xaml.cs:1211-1220` 传入）在 UI 线程构造， Tick 亦在 UI 线程——链路闭环。
4. **Dispose 竞态防护**：`_disposed` 检查 + 先置零句柄再 `UnhookWinEvent`（L148-160），回调入口二次判 `_disposed`（L108）。虽 `_disposed` 非 volatile，且 WinEvent 回调与 UI 线程 Dispose 理论同线程（out-of-context 投递），实际无竞态窗口。

另复核显示桌面链路同源的 `DisplayTopologyTransitionCoordinator`（Task_Tick 异步恢复、`_isExecuting` 重入闸 + generation 比对）与 `AppLifecycleRecoveryWatcher`（subclass 窗口消息天然 UI 线程 + 去抖 timer），投递纪律同样完备。

### THR-01 ThemeService.RefreshAppearance 经 Task.Run 在线程池线程触碰 WinUI 对象并触发跨线程事件处理

- 【位置】`src/DeskBox/App.xaml.cs:941`（`var themeTask = Task.Run(() => themeService.RefreshAppearance());`）；`src/DeskBox/Services/ThemeService.cs:206-211`（`RefreshAppearance` 本体）、`ThemeService.cs:130-141`（`TrackWindow` → `_trackedWindows.Add`）、`ThemeService.cs:198-204`（`ApplyToAllWindows`）

- 【风险等级】**P1**
- 【潜在影响】`RefreshAppearance → ApplyToAllWindows` 在线程池线程上遍历 `_trackedWindows` 并调用 `ApplyToWindow`：读取 `window.Content`（WinUI 对象跨线程读取，可抛 RPC_E_WRONG_THREAD）、调用 `AccentResourceScope.Apply(rootElement, ...)`（写 XAML 依赖属性，跨线程写入可抛异常或破坏渲染状态）；同时 `AppearanceChanged?.Invoke()` 在后台线程触发订阅者——`App.Tray.cs:849-858 UpdateTrayIconAppearance` 直接 `_trayIcon.Icon = ...`（H.NotifyIcon 托盘句柄操作）、`WeatherWidgetContent.xaml.cs/TodoWidgetContent.xaml.cs` 的订阅者虽有 `HasThreadAccess` 再投递保护（安全），但托盘订阅者**没有**任何投递保护。并发面上，启动期间 UI 线程的 `TrackWindow`（`CreateTrayIcon`，App.xaml.cs:945）与后台 `RefreshAppearance → ApplyToAllWindows` 同时读写 `List<Window> _trackedWindows`（非线程安全集合，无锁）——`List<T>` 并发 Add/枚举可抛 `InvalidOperationException` 或产生脏读。
- 【根因说明】启动阶段并行化时把整个 `RefreshAppearance`（本应只在 UI 线程执行，内部含 XAML 赋值与事件广播）整体丢进 `Task.Run`；`_trackedWindows` 字段与 `AppearanceChanged` 事件均无线程归属声明。
- 【整改建议】两选一：(a) 最小修复——`Task.Run` 内只包离线可做的工作（如读取系统色值），`RefreshAppearance` 留在 UI 线程；或 (b) 在 `RefreshAppearance` 入口补 `HasThreadAccess` 判断并 `TryEnqueue` 重投（与 `ApplyToWindow` L164-168 已有模式一致），同时给 `_trackedWindows` 的增删/枚举加锁。托盘订阅者 `UpdateTrayIconAppearance` 建议同批补 TryEnqueue 投递，消除对调用线程的隐式假设。
- 【证据】

### THR-02 ReservedHotkeyHookService.TryStart / Stop / DesktopDoubleClickActivationService.TryStart / Stop 在 UI 线程同步等待（最坏 ~2.15 秒），刷新注册时卡 UI

- 【位置】`src/DeskBox/Services/ReservedHotkeyHookService.cs:138`（`ready.Task.Wait(StartupTimeoutMilliseconds)`）、L197（`thread.Join(StopTimeoutMilliseconds)`）、L235（`thread.Join(ForcedStopTimeoutMilliseconds)`）；`src/DeskBox/Services/DesktopDoubleClickActivationService.cs:161`（`ready.Task.Wait(1500)`）、L213-229（`Join(500)` + `Join(150)`）
- 【触发条件】a) 用户在设置页改热键 / 触发 `GlobalHotkeyService.RefreshRegistration`（每次 `TryApplyActivation`、`SetEnabled`、生命周期恢复 `OnLifecycleRecoveryRequested → RefreshRegistration` 都会走 `Stop→TryStart`）；b) 系统唤醒/Explorer 重启后 `App.xaml.cs:1298-1299` 对两个服务同时 `RefreshRegistration`；c) 钩子线程假死（`GetMessage` 停滞或钩子回调阻塞）时 `ready.Task.Wait` 吃满 1500ms + `Join(500)` + `Join(150)`。
- 【风险等级】**P2**
- 【潜在影响】全部调用点都在 UI 线程：正常路径 `Stop` 的 `thread.Join(500)` 通常瞬间返回（WM_QUIT 已投递），但钩子线程卡在 `KeyboardHookProc`（LL 钩子回调被系统串行化）或 explorer 假死场景下，UI 线程会被同步阻塞最长 `500+150`（Stop）+ `1500`（TryStart 超时）≈ 2.15 秒，表现为设置页/热键切换瞬间冻结。`OnLifecycleRecoveryRequested` 在 unlock 恢复场景连发两次刷新，感知更明显。

### THR-07 StoreStartupService.GetStartupTask 在 UI 线程同步 GetAwaiter().GetResult()

- 【位置】`src/DeskBox/Services/StoreStartupService.cs:89-92`（`StartupTask.GetAsync(StartupTaskId).AsTask().GetAwaiter().GetResult()`）；调用方 `IsEnabled/Enable/Disable`（L9-87）
- 【触发条件】设置页/启动流程查询或切换"开机自启"（MSIX 发布形态时）。
- 【风险等级】**P3**
- 【潜在影响】`StartupTask.GetAsync` 是 WinRT 异步 IPC 调用（跨进程到 StateRepository），UI 线程同步等待通常数十毫秒，系统繁忙时可至数百毫秒；代码作者在 `Enable` 内部已意识到 `RequestEnableAsync` 阻塞会死锁并做了 fire-and-forget（L37-50 注释），但 `GetAsync` 的同步等待未做同等处理——同一次点击 UI 线程仍被 IPC 串行阻塞。
- 【根因说明】同步接口 `IStartupService` 设计迫使 async WinRT 调用同步化。
- 【整改建议】`IStartupService` 增加 `Task<bool> IsEnabledAsync()` 异步形态，设置页异步刷新；或至少将查询结果在启动早期后台缓存。
- 【证据】
  ```csharp
  // StoreStartupService.cs:89-92

  {
      return StartupTask.GetAsync(StartupTaskId).AsTask().GetAwaiter().GetResult();
  }
  ```
