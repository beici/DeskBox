## 2. 已知问题复核（DEF-006 相关广播链路）

### 2.1 结论：修复成立，未发现新的广播缺陷

DEF-006（点击格子标题区域时其他格子闪烁）的修复采用专用合批方法，本轮对完整链路复核如下：

1. **触发端**：`ContentWidgetWindow.WindowInteraction.cs:179`（`TitleBarGrid_PointerPressed` → `App.Current.WidgetManager?.ActivateAllVisibleWidgetsFromTitle(HWnd)`，仅在标题浮出且非 Ctrl 时触发）；`QuickCaptureWidgetWindow.WindowInteraction.cs:51` 同路径。
2. **广播端**：`WidgetManager.ZOrder.cs:404-421` `ActivateAllVisibleWidgetsFromTitle` 收集全部可见窗口句柄 → `WidgetLayerService.BringTitleActivatedGroupToFront(handles, activeHwnd)`（`WidgetLayerService.cs:584-660`）：
   - 仅被点击窗口执行 TOPMOST 置顶→清除的带迁移往返；
   - 其余 peer 通过**单次 `BeginDeferWindowPos` + 逐个 `DeferWindowPos` + `EndDeferWindowPos`** 在同一带内直接插到激活窗口之后（`SWP_NOACTIVATE|SWP_NOOWNERZORDER`），无带迁移、无 DWM 重合成风暴。
3. **延迟恢复端（2300ms）**：`QueueTemporaryRaisedWidgetRestore` → `RestoreTemporarilyRaisedWidgetsToDesktopLayerCore`（`WidgetManager.ZOrder.cs:176-280`）。注意 `TrackTemporarilyRaisedWidgets(handles, "title-activated-all")` 跟踪了**全部**可见窗口（含从未升带的 peer），恢复时对每个窗口调用 `ForceRestoreDesktopLayerFromManager` → `RestoreDesktopLayer(force:true)` → `ClearTopMostOnly`：
   - 对 peer 而言 `ClearTopMostPreservingForeground` 是同带 no-op（peer 从未进入 TOPMOST 带），不产生带迁移闪烁；
   - 恢复受 `_widgetsRaisedFromTray / _isTogglingWidgetsDesktopLayer / _sessionManager.IsInteractionActive / HasActiveExpandedWidgetLayerLease()` 四重门控（`WidgetManager.ZOrder.cs:218-240`），用户正在交互或任一胶囊展开租约活跃时延迟并最终由 `ReleaseExpandedWidgetLayer`（同文件 :100-103）兜底触发，不会强拆展开中的胶囊；
   - 每窗恢复后的 `QueueIdleWidgetZOrderNormalization`（120ms 归一化）由 `_idlePeerOrderGeneration` 代际去重，仅最后一次真正执行，无广播风暴。
4. **副作用面**：恢复广播会对从未点击的 peer 调用 `_contentHost.OnDeactivated()`。该行为在修复前（`BringGroupTemporarilyToFront` 托盘路径同样恢复全部已升窗口）即存在，属"组级激活语义"的既定设计；`WidgetShellContentHost.OnDeactivated`（`WidgetShellContentHost.cs:266-274`）有 `_isActivated` 幂等保护，且内容级 `OnDeactivated` 实现均为空转（如 `TodoWidgetContentAdapter.OnDeactivated` 为空方法），影响有界。

**复核结论：修复链路成立；单次点击的 DWM 带迁移仅发生在被点击窗口一个 HWND 上；未发现会重新引入 peer 闪烁或产生级联广播的路径。** 与修复文档 `docs/quality/batch-2/BUG-C1-title-click-flicker.md` 声明一致。

## 3. 问题清单（风险降序）

### 【EVT-01】ThemeService.AppearanceChanged 广播无逐处理器异常隔离，单个订阅者异常会静默截断全部后续订阅者的主题通知

- 【位置】`src/DeskBox/Services/ThemeService.cs:206-211`（raise 点）；对比 `src/DeskBox/Services/LocalizationService.cs:138-155`、`src/DeskBox/Services/SettingsService.cs:923-943`（同类广播均有隔离）
- 【触发条件】`AppearanceChanged` 的任一订阅者在处理中抛异常。现实可抛点：`WidgetManager.ApplyAppearancePreview`（`WidgetManager.cs:668-686`）内部 `foreach (window) window.ApplyAppearancePreview()` 逐窗口调用仅有 try/finally、无 per-window catch，任一窗口外观应用失败即向外抛出；该异常从 `RefreshAppearance()` 内 `AppearanceChanged?.Invoke()` 处中断广播。
- 【风险等级】P2（低频边界场景；后果为多窗口主题静默不一致 + 异常进入吞异常通道）
- 【潜在影响】订阅顺序为 App 托盘图标（`App.Tray.cs:203`）→ WidgetManager（`WidgetManager.cs:438`）→ 各窗口/内容控件（Todo `TodoWidgetContent.xaml.cs:167`、Weather `WeatherWidgetContent.xaml.cs:93`、SettingsViewModel、SettingsWindow、SearchPopupWindow）。若中段订阅者抛出，排在后面的全部内容控件的本地主题资源、segmented 样式、editor 视觉不刷新，直到下次主题变更；若调用点在 `_appearanceDebounceTimer.Tick`（`ThemeService.cs:38`）内，异常进入 WinUI 未处理异常通道，被 `App.OnUnhandledException`（`App.xaml.cs:269-274`）以 `e.Handled = true` 吞掉，**无崩溃信号、无用户可感知提示**。
- 【根因说明】`ThemeService.RefreshAppearance` 采用裸 `AppearanceChanged?.Invoke()`，与本项目 `LocalizationService.RaiseLanguageChanged`、`SettingsService.NotifySettingsChangedSafely` 已确立的"逐处理器 try/catch 快照遍历"广播规范不一致。
- 【整改建议】将 raise 改为 `GetInvocationList()` 快照 + per-handler try/catch（照抄 `LocalizationService.RaiseLanguageChanged` 的实现与注释约定）；同时建议在 `ApplyAppearancePreview` 的 foreach 内对单窗口加 per-window catch，避免一个窗口的失败阻断其余窗口的预览。
- 【证据】
  ```csharp
  // ThemeService.cs:206-211
  public void RefreshAppearance()
  {
      ApplyToAllWindows();
      AppearanceChanged?.Invoke();          // ← 裸调用，无隔离
      App.ScheduleLightMemoryCleanup();
  }
  // WidgetManager.cs:668-686（无 per-window catch，异常可穿出）
  _isApplyingAppearancePreview = true;
  try {
      foreach (IDesktopWidgetWindow window in GetLoadedDesktopWindows())
          window.ApplyAppearancePreview();
  } finally { _isApplyingAppearancePreview = false; }
  // 对照组（已有隔离）：SettingsService.cs:934-943
  Delegate[] handlers = SettingsChanged?.GetInvocationList() ?? [];
  foreach (Action handler in handlers.Cast<Action>()) {
      try { handler(); } catch (Exception ex) { App.Log($"[SettingsService] SettingsChanged observer failed: {ex}"); }
  }
  ```

### 【EVT-02】TodoItem_DataContextChanged 只订阅新 item、从不退订旧 item，容器复用后旧 TodoItemViewModel 残留订阅

- 【位置】`src/DeskBox/Controls/WidgetContents/TodoWidgetContent.DragDrop.cs:578-600`；处理体 `TodoWidgetContent.ListInteraction.cs:208-236`；Adapter 清理路径 `TodoWidgetContentAdapter.cs:233-251`
- 【触发条件】ListView 容器复用（过滤切换、滚动、项增删导致 DataContext 从 item A 换为 item B）。
- 【风险等级】P3（订阅者与被订阅者同生命周期，泄漏有界；影响为冗余回调与无效扫描）
- 【潜在影响】旧 item VM 的 `PropertyChanged` 委托持续指向 Todo 视图；此后该不可见 item 的 `IsCompleted`/`ColorMarker` 变更仍触发 `TodoItem_PropertyChanged`，对 `TodoListView.Items` 做 `ContainerFromItem` 全可见列表扫描后一无所获。随使用时长，订阅集合单调增长（每个曾被展示过的 item 残留一条）。ViewModel（含 item VM）与 adapter 同生命周期（`TodoWidgetContentAdapter.cs:33-56` 每次 `CreateDetachedContent` 新建 ViewModel），故不跨内容窗口、不构成跨代泄漏；但 `Adapter.Dispose` 仅调用 `ReleaseTransientRenderingSubscriptions`，**未清理 item 级订阅**，若未来 ViewModel 生命周期被拉长（如胶囊/表面共享 store），将升级为悬空回调触碰已关闭窗口视觉树的缺陷。
- 【根因说明】WinUI `DataContextChangedEventArgs` 仅携带 NewValue，处理器以"`DataContext is TodoItemViewModel` 即 `-=` 再 `+=`"防御，退订目标错位为"新 item"，旧 item 永不解除。
- 【整改建议】在容器（sender）上缓存上次订阅的 item（如 `Tag` 或WeakReference 字典），DataContextChanged 时先对旧 item `-=`；或在 `TodoWidgetContent.Unloaded` / `Adapter.Dispose` 中遍历 `ViewModel.VisibleItems` 与缓存解除。另注意 `ListInteraction.cs:247-252` 的 `ApplyTodoItemTooltips` 已退化为空实现（`_ = localization;`），属死代码卫生问题，可在同批次清理。
- 【证据】
  ```csharp
  // TodoWidgetContent.DragDrop.cs:578-587
  private void TodoItem_DataContextChanged(FrameworkElement sender, DataContextChangedEventArgs args)
  {
      if (sender.DataContext is not TodoItemViewModel item) { return; }   // ← 换出为 null/非 item 时不做任何退订
      item.PropertyChanged -= TodoItem_PropertyChanged;                   // ← 作用于"新" item
      item.PropertyChanged += TodoItem_PropertyChanged;
  ```

### 【EVT-03】App.OnUnhandledException 对全部未处理异常一律 e.Handled=true，事件链中途异常被静默吸收、无告警升级

- 【位置】`src/DeskBox/App.xaml.cs:269-274`
- 【触发条件】任意 UI 事件处理器或 async void 事件处理器抛出未捕获异常（仓库中存在大量 `async void` 事件处理器，如 `TodoWidgetContent.ListInteraction.cs:22/74/260/312/333`、`FileSurfaceContent` 与 QuickCapture 各处）。
- 【风险等级】P3（策略选择；与本专项相关的部分是"广播中断不可观测"）
- 【潜在影响】与 EVT-01 叠加：任何广播链（含 routed event 多订阅者）中途的异常被记录日志后流程继续，后续订阅者/后半段处理器被跳过，状态半更新且仅有一行日志。好处是避免崩溃，坏处是事件相关缺陷无用户可见信号，回归发现依赖日志巡检。
- 【根因说明】全局兜底吞异常策略；源侧隔离（SettingsService/LocalizationService 模式）仅在两处主干广播存在，其余广播源与事件处理器依赖该兜底。
- 【整改建议】保留兜底但：(a) 按第 1 节整改补齐 ThemeService 等广播源侧隔离；(b) 在 `OnUnhandledException` 中对关键广播上下文（如含 `AppearanceChanged`/`SettingsChanged` 调用栈）升级日志级别或计数上报到 `PerformanceLogger`/诊断包，使"广播被截断"可被诊断包捕获。
- 【证据】
  ```csharp
  // App.xaml.cs:269-274
  private void OnUnhandledException(object sender, Microsoft.UI.Xaml.UnhandledExceptionEventArgs e)
  {
      Log($"Unhandled exception: {e.Exception}");

  }
  ```
