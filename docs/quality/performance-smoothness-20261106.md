# 2026-11-06 动画时序与文件刷新专项

本轮基于工作区已有的 11 月 5 日性能优化继续推进，修复三条可复现的机制问题：胶囊进度与自适应提交节奏失配、托盘错峰视觉提前播放、大目录刷新先按枚举顺序再按用户顺序重排。沿用统一格子宿主、共享帧调度、Win32 批量位置提交和 Composition 动画；没有新增依赖、配置项或数据迁移。

## 设计与改动

### 胶囊展开与收起

此前最大进度步长只在动画启动时按初始刷新率计算。提交器因真实负载降低频率后，正常的较慢提交仍被旧步长判作卡顿，造成额外减速，恢复预算耗尽后又突然加快。

`WidgetCompactTransitionProgressPolicy.ResolveStep` 现在接收当前 `TargetIntervalMilliseconds` 和剩余恢复预算。正常适配间隔全量推进，真正的长帧只吸收预算内的超额时间；时间戳保持单调。首帧归零、冷内容等待、视觉重新同步及完成看门狗保持原有职责。

### 文件刷新与排序

`WidgetItemCollectionReconciler` 先按路径合并快照并保留项目对象，再形成稳定的最终顺序，最后协调 `ObservableCollection`。自动和手动顺序共用对象合并入口，图标与已有 Shell 元数据继续由 `ApplyRuntimeItemData` 决定保留。

- 无变化快照只进行线性检查，不发集合通知，也不经过枚举顺序。
- 真实重排使用最长递增子序列保留已有相对顺序，使保留项的 `Move` 次数最少；插入、删除按最终成员关系处理。
- 连续新项目按正向插入，避免首次装载时反复移动刚插入的项目。
- `WidgetStackProjectionInvalidationPolicy` 显式识别实际影响栈分类及栈内排序的元数据变化，经既有调度器合并刷新，不再依赖临时重排产生的副作用。
- 相同路径大小写及重复快照沿首项优先规则处理；保留项的选择、剪切及已加载状态随对象保留。

无变化路径为 O(n)，需要排序时的目标序列生成是 O(n log n)。真实大范围重排仍受 `ObservableCollection` 底层数组移动约束，最坏可达 O(n²)；本轮减少了不必要移动及 UI 通知，没有宣称任意重排都变成线性。

### 托盘错峰动画

此前收集批次条目时便启动透明度、缩放、旋转和裁剪动画，而 HWND 位置要等内容首帧及每窗错峰延迟。现在控制器先固定完整起始姿态，由批次驱动器在每条目的第一个有效帧调用一次 `StartVisual`。晚到帧通过 Composition 的动画控制器定位到相同线性进度，后续仍独立在合成器运行。

视觉启动位于位置去重前，因此纯淡入、缩放、擦除等零位移效果正常播放。尚未开始便被取消、替换或失效的条目不会启动旧视觉动画。没有更改 Z-order、桌面 Owner 或原生窗口生命周期顺序。

## 可验证的工作量变化

- 8 种自动排序组合各使用 5,000 项相同快照：排序检查严格为 **4,999 次比较、零集合通知、零项目属性通知**，对象顺序和身份保持。
- 旧 `Items.IndexOf` 全扫描在 5,000 项已排序列表上的理论比较量为 **12,502,500 次**。该数字是旧算法的工作量推导，不是实测耗时。
- 720 种六项排列验证最少 `Move` 数；100 组随机增删验证最终顺序、身份、通知及无 `Reset`。
- 第一项元数据变化后需要排到末尾时，只发出一次 `Move`。
- 26 项进度策略测试覆盖适配频率、显示器频率切换、恢复预算尾部、重复卡顿与非法时钟输入。
- 17 项分栈失效测试覆盖日期桶、名称排序、保留的 AddedAt/ShellKind 以及不影响投影的元数据。
- 7 项新增托盘行为测试使用可控帧时钟，覆盖首帧等待、空间错峰及迟到进度、零位移、取消、失效、启动异常与替换批次。

上述结果证明算法工作量和时序行为，不等价于屏幕呈现 FPS，也不用于推导整机 CPU 或内存下降百分比。
